# МУЗЫКА — Fix #283: очередь воспроизведения плейлиста обрезана (100+ треков)

> Жалоба: «Почему при воспроизведении плейлиста в 100 треков или более список
> на воспроизведение не соответствует количеству треков».
> Дата: 2026-09-07. Коммит: см. HISTORY 2026-09-07 (Fix #283).

## Диагноз

VK отдаёт `audio.get` (в т.ч. с `album_id`) **страницами** — жёсткий кап ~100 треков на
запрос. В PinoK плейлист загружался ОДНОЙ страницей в 5 местах:

| Место | До фикса | Следствие |
|---|---|---|
| `MusicScreen.openPlaylistAndPlay` (плейлист каталога → «Играть») | `audioGetPlaylistById` без count → **50** | очередь = первые 50 |
| `PlaylistDetailScreen` (детали плейлиста) | `count = 100`, без догрузки | очередь = первые 100 |
| `MusicScreen` PlaylistsDialog ×3 (play/download) | `audioGetPlaylistTracks` дефолт **50** | очередь/скачивание = 50 |
| `PlaylistAttachmentCard` (вложение-плейлист в посте) | `count = 100`, без догрузки | очередь = 100 |

Сама очередь `PlayerConnection.playTrackList` лимита НЕ имеет (проверено: весь список
идёт в `setMediaItems`) — узкое место только в загрузке.

## Фикс (центральный, все 5 мест закрыты одним изменением API-слоя)

1. **`audioGetPlaylistTracks`** — теперь авто-догрузчик: цикл страниц
   (`page = count.coerceIn(10,100)`), пока не набрано `total` из первого ответа /
   страница пуста / неполная; дедуп `(ownerId,id)` (паттерн Fix #281);
   страховка `MAX_PLAYLIST_PAGES = 60` (≤6000 треков); `quality=hq` читается один раз
   до цикла (не per-страница из DataStore); rate-limiter (3 rps) троттлит цикл штатно.
   Возвращает `(total, ВСЕ треки от offset)` — прежние вызовы без ручной пагинации
   получают полный хвост плейлиста.
2. **`audioGetPlaylistById`** — inline `audios[]` считается первой страницей; при
   `playlist.count > собрано` идёт догрузка тем же циклом (dedup на стыке offset);
   ветка сообществ (`audios[]` нет) покрывается авто-догрузчиком из п.1.
   Новый trailing-параметр `onProgress: ((loaded, total) -> Unit)? = null` —
   дефолт null, все прежние вызовы совместимы.
3. **`PlaylistDetailScreen`** — подписка на прогресс: под спиннером «Загружено N из M…».
4. **`MusicScreen.openPlaylistAndPlay`** — `count = 100` (меньше round-trip'ов).

## Что НЕ менялось

- `parseAudioResponseWithCount`, `audioGet` (основной список с его hasMore-пагинацией),
  поиск (`audioSearchWithSections`), `PlayerConnection` — не тронуты.
- Фильтр `!url.isNullOrBlank()` перед `playTrackList` остался: треки без URL
  (рестрикты лицензирования) невозможно воспроизвести; очередь = все воспроизводимые.
  Это редкий случай; для полных плейлистов счётчик совпадает с `playlist.count`.

## Матрица проверки (юзером, после сборки)

1. Плейлист 100+ (свой): детали → «Играть» → в очереди плеера = количеству треков
   плейлиста; во время загрузки виден «Загружено N из M…».
2. Плейлист каталога VK Музыки 100+ → тап «Играть» → Toast «Плейлист … — N треков»,
   N ≥ 100, очередь = N (минус рестрикты).
3. Вложение-плейлист в посте → play → очередь полная.
4. Диалог «Плейлисты» (из профиля/поста) → play и download → полный список.
5. Плейлист < 100 — поведение не изменилось (одна страница, быстрее).
6. Плейлист сообщества (owner_id<0) — тоже полный (ветка audio.get album_id).
