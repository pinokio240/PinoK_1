## §3. Узкие места по приоритетам

### P0 — критично, делать первым

#### P0-1. `VKApiClient.kt` = 17 735 строк, 1 god object
- 492 функции, из них 399 suspend, 989 обращений к JSONObject.
- Проблемы: медленная компиляция, merge-конфликты, IDE-лаги, отсутствие юнит-тестов, когнитивная нагрузка.
- **Решение — разбить на под-фасады через extension-функции (без ломания call-sites):**
  ```
  api/
    VKApiClient.kt         (ядро ~500 строк: call, retry, interceptors)
    VKApiAuth.kt
    VKApiMessages.kt
    VKApiFeed.kt
    VKApiMusic.kt
    VKApiVideo.kt
    VKApiCalls.kt
    VKApiChannels.kt
    VKApiCommunity.kt
    VKApiFriends.kt
    ...
  ```
- Ничего у существующих вызовов не ломается — методы остаются доступны через тот же экземпляр.

#### P0-2. Baseline Profile отсутствует
- Compose-приложения без baseline profile прогреваются на 30–50% медленнее.
- Внедрение через Jetpack Macrobenchmark (модуль `:baselineprofile`).
- **Ожидаемый эффект: −20–40% холодного старта и первого рендера.**
- Не требует изменений существующего кода.

#### P0-3. Аудит ProGuard-правил
- В `app/proguard-rules.pro` есть избыточные `-keep`:
  - `-keep class androidx.compose.** { *; }` — сохраняет всю Compose; обфускация отключена; **слишком широко**.
  - `-keep class androidx.media3.** { *; }` — то же для Media3.
  - `-keep class re.pinok.data.model.** { *; }` — нужно ТОЛЬКО если используется Gson-рефлексия; у нас вручную через `JSONObject` → можно снять.
- **Ожидаемый эффект: −5–15% APK size.** Требуется эмпирическая проверка (собрать release → проверить, что всё работает).

### P1 — важное, делать после P0

#### P1-1. Дробление гигантских Compose-экранов
- `ChatDetailScreen.kt` (494 КБ, ~14 000 строк): вынести bubble, menu, attachment-row и т.д. в отдельные файлы.
- `SettingsScreen.kt` (455 КБ): вынести секции в отдельные файлы.
- **Эффект:** точнее рекомпозиция Compose, быстрее IDE, меньше конфликтов.

#### P1-2. Разгрузить `SovaApp.kt` (169 КБ)
- Application тянет всё: контейнеры, OkHttp/Coil, session-cookies, WorkManager, R8, планирование, LongPoll.
- **Решения:** ленивая инициализация (`androidx.startup`), отложенные задачи, splashing API.
- **Ожидаемый эффект: −200…500 мс холодного старта.**

#### P1-3. R8 full mode
- `android.enableR8.fullMode=true` в gradle.properties.
- **Эффект: −3…8% APK size, быстрее runtime.**

#### P1-4. Configuration Cache (с оговоркой)
- В `gradle.properties` сейчас отключён (конфликт с AGP 9.x + Studio).
- После стабилизации — попробовать на ветке.
- **Ожидаемый эффект: −30…50% Gradle sync/build.**

### P2 — желательно, но не срочно

- Очистить `app/build/` (509 МБ): `gradlew clean`.
- Аудит Compose-аннотаций (`@Stable`, `@Immutable`, `derivedStateOf`, `key(...)` в LazyColumn).
- Вынести retry Coil из VKApiClient (комментарий про 1580 строк ретраев).
- Обновить зависимости (Compose BOM 2025.06.00 → свежее, Coil 3.3.0 → свежее).
- Разделить gradle.properties (общее) и local.properties (машинное).

## §5. Что делать в первую очередь (топ-3)

1. **Baseline Profile** — 1 день, самый заметный эффект для пользователя (холодный старт −20…40%), не трогает существующий код.
2. **Разбить `VKApiClient.kt`** — самое большое узкое место для разработки. Можно делать без остановки релизов: extension-функции в новых файлах, старые вызовы не трогаются.
3. **Аудит ProGuard** — потенциально −5…15% APK за 2–3 часа на проверку.

---

## §6. Что НЕ рекомендуется

- Ломать архитектуру `#ARCH-CONTAINERS` — она валидируется опытом сторонних проектов (см. `analysis_vs_pinok.md`).
- Переписывать на Hilt/Koin — уже есть `ContainerRegistry`.
- Заменять `JSONObject` на kotlinx.serialization — 989 мест, риск огромен.
- Переходить на Kotlin Multiplatform — не ваш кейс.

## §7. План внедрения (по волнам)

Правила из `контейнеры.план.md` соблюдаются: каждый этап = отдельный коммит + push + запись в `worklog.md`; приложение собираемо после каждого этапа.

### Волна O1 — Baseline Profile
1. Создать Gradle-модуль `:baselineprofile` (com.android.test + androidx.baselineprofile).
2. Написать `BaselineProfileGenerator` — сценарий: запуск приложения → переход в Messages → открытие чата → переход в Feed.
3. Прогнать на реальном устройстве → `app/src/main/baseline-prof.txt`.
4. Подключить в `:app` через `baselineProfile(project(":baselineprofile"))`.
5. Измерить до/после через Macrobenchmark.

### Волна O2 — Split VKApiClient
1. Выделить ядро `VKApiClient.kt` (call, retry, interceptors, HTTP).
2. Вынести группы методов в extension-файлы по доменам (auth, messages, feed, ...).
3. После каждого шага — `gradlew :app:compileDebugKotlin` + локальный smoke-тест.
4. В конце — удалить из ядра всё, что переехало.

### Волна O3 — ProGuard/R8 тюнинг
1. Снять слишком широкие `-keep` (`androidx.compose.**`, `androidx.media3.**`, `re.pinok.data.model.**`).
2. Проверить release-сборку на устройстве: логин, мессенджер, музыка, звонки, видео, каналы.
3. Включить `android.enableR8.fullMode=true`.
4. Сравнить APK до/после по размеру.

### Волна O4 — Дробление Compose-экранов + SovaApp
1. `ChatDetailScreen.kt` → 10–15 файлов-компонентов.
2. `SettingsScreen.kt` → файлы по секциям.
3. `SovaApp.kt` → вынести инициализацию в под-функции + androidx.startup.
4. Замер холодного старта.

### Волна O5 — Остальное (P2/P3)
1. Чистка `app/build`. `gradlew clean`.
2. Аудит Compose-аннотаций (`@Stable`, `@Immutable`, `derivedStateOf`, `key`).
3. Обновление зависимостей по одной (Compose BOM → Coil → OkHttp).
4. Разделить gradle.properties / local.properties.

## §8. Что НЕ входит в этот план

- Обфускация/шифрование API-ключей — обсуждается отдельно.
- Замена Compose XML — не рассматриваем.
- Переезд на другой DI — не рассматриваем.
- Смена базы данных (если сейчас DataStore, Room) — не рассматриваем.

## §9. Приложение — какие метрики мерять

- **Холодный старт**: `adb shell am start -W -n re.pinok/.ui.MainActivity`.
