### 0.3. Метод (проверен на снапшотах звонков)

1. Python, чтение **cp1251**: вырез `<script>/<style>` → регэкспы на `aria-label`, `title`,
   `data-testid`, видимый текст (дедуп) → инвентарь контролов (§1).
2. Инлайн-скрипты страниц: извлечение встроенного `apiPrefetchCache` — 24 записи
   `{method, request{параметры}, version 5.288, response}` (§2 — **параметры официальные, из запросов**).
3. Регэксп-скан JS-бандлов (`utf-8/replace`) на `"модуль.метод"`: профиль-специфичный
   `pageProfile.a8b48616.js` (548 КБ), `core_spa`, `common`, `notifier`, `likes`, `wall`,
   `privacy`, `settings`, `loader_nav` + поиск legacy-endpoints `al_*.php` и i18n-ключей `lang0_2.js`.
4. Сверка с кодом PinoK: полный список методов `VKApiClient.kt` (`rg 'suspend fun \w+'`, ~300 шт.),
   точечные `rg` по экранам `:app` (`ProfileScreen.kt` 788 строк, `UserProfileScreen.kt` 451 строка,
   `NotificationSettingsScreen.kt`, `SettingsScreen.kt`, `SovaNavHost.kt`, `SovaApp.kt`, `:contracts`).

## §3. Анализ готового кода «Контейнер Профиль» (от юзера)

### 3.1 `ProfileContainer.kt` (915 B)

Реализовано: `AppContainer` с `id="profile"`, capability `ProfileNavEntry`
(title «Профиль», iconKey `profile`, order 4, route `profile`) и `ProfileSettingsSection`
(title «Профиль», order 2, route `profile_settings`); `init/release` — пустые.
Импорты контрактов корректные (`re.pinok.contracts.{AppContainer, Capability, NavEntry, SettingsSection}`).

**Не соответствует канону и не интегрировано:**

1. **Не зарегистрирован.** В `SovaApp.onCreate` регистрируются только calls (:686),
   photos (:700), audio (:717); лог «контейнеров=3» — профиль отсутствует (SovaApp.kt:686–730).
2. **Конфликт маршрута с ядром.** `route = "profile"` уже занят ядерным `Screen.Profile`
   (`Screen.kt:43`, destination `SovaNavHost.kt:1482` → ядерный `ProfileScreen`). По правилу
   владения UI (контейнеры.план.md, Часть 1) «Профиль» — ядерный пункт; NavEntry с тем же
   route задвоит пункт drawer. Требуется решение: профиль НЕ контейнеризуется как NavEntry,
   либо NavEntry уходит, а контейнер публикует только SettingsSection/рендеры.
3. **Хост-маппинги отсутствуют.** `hostDestinationForRoute` (SovaNavHost.kt:191) знает только
   `calls_history/photos/equalizer`; `hostIconForKey` (:209) не знает ключ `profile` →
   отрисовалась бы нейтральная иконка «расширение»; `hostSettingsContentFor`
   (SettingsScreen.kt:319) не знает `profile_settings` → вкладка настроек пустая.
4. **Нет `SettingsSection`-контента**: контейнер объявляет вкладку настроек, но кода вкладки
   (какой контент рендерить по `hostSettingsContentFor("profile_settings")`) в архиве нет.
5. **Нет фасада зависимостей.** Канон §3.2-Б требует `ProfileDependencies` (интерфейс в
   контейнере) + `LocalProfileDeps = staticCompositionLocalOf { error(...) }` (fail-fast)
   + реализацию в ядре (`SovaApp : ProfileDependencies`, фасад `ProfileApi` по образцу
   `CallsApi`) + port capability. Ничего из этого нет — контейнер «каркас ради каркаса».

**Заглушки и дефекты:**

без правок):**

1. `api.photosGetAll(ownerId = userId, count = 20)` (:99) — метода **нет** в VKA (MISS).
2. `import re.pinok.data.model.AudioTrack` (:29) и `List<AudioTrack>` (:71) — класса **нет**

3. `profile?.online == true` (:181, :190) — `UserProfile.online` имеет тип **Int** (:27

## §4. Пробелы и риски

### 4.1 Пробелы «снапшот → код» (не покрыто ничем)

1. **Редактирование профиля**: `account.saveProfileInfo` + upload-цепочки аватара/обложки
   (`photos.getWallUploadServer`+`photos.save`, обложка×3) — API ❌ + UI ❌. Крупнейший
   функциональный пробел «своего» профиля.
2. **Статус**: `status.set` — API ❌, правка UI ❌.
3. **Обложка профиля**: модель есть (`UserProfile.cover`), API ❌, UI ❌.
4. **Вкладки профиля**: API `usersGetContentTabs`/`usersGetWallTabs` есть, UI нет; подвкладки
   стены (все/owner/архив) — `wallGetWithFilter` есть, UI нет.
5. **Фото**: `photos.getAll` — API ❌ (блокер фото-вкладки), `photos.getAlbumsCount`,
   `photos.photoFeedGet` — ❌; UI фото-вкладки/альбомов в профиле нет.
6. **Статьи** (`articles.getOwnerPublished`) и **рассказы** (`narratives.getFromOwner`) — API ❌.
7. **Подарки профиля** (`gifts.get`) — API ❌ (каталог отправки есть); секция/иконка в шапке — ❌.
8. **Подписки** (`users.getSubscriptions`) — API ❌; экран подписчиков/подписок — ❌.
9. **«Возможно, вы знакомы»** в профиле — UI ❌ (API есть; у кода юзера — каркас с дефектами).
10. **Приватность VK** (30+ ключей с исключениями) — BFF API есть, UI ❌; legacy
    `al_settings.php`-путь веба в PinoK не воспроизводится (и не нужен — BFF закрывает).
11. **Уведомления групп** (§1.5) — нет ни API-обёртки BFF-ключей, ни UI (частичный аналог —
    `groups.editNotifications`).

    частично (баланс), риск: VK может не отдавать этот endpoint не-браузеру.
13. **Жалоба** (`users.report`) — API ❌ (есть только `reportVideo` для клипов) + UI ❌.
14. **`wall.markAsSpam`**, **`fave.addUser/removeUser`**, **`friends.deleteSubscriber`** — API ❌.

### 4.2 Риски

1. **Канон vs готовый код**: «Контейнер Профиль» не собирается даже теоретически (5 ошибок
   компиляции в ProfileScreen.kt, §3.2) и конфликтует с ядром по маршруту `profile`.
   Внедрение «как есть» сломает сборку; код юзера стоит рассматривать как прототип UI-идей
   (вкладки, «Возможно, вы знакомы»), а не как переносимый модуль.
2. **Правило владения UI**: профиль — ядерный раздел (как Лента/Сообщения); канон §3.7
   не ставит профиль в очередь контейнеризации. Контейнеризация профиля потребовала бы
   решения пользователя, противоречащего текущему канону. Более безопасный путь — развитие
   ядерных `ProfileScreen`/`UserProfileScreen` + новые методы в `VKApiClient` (фасады не нужны).
3. **fields-дисбаланс**: веб запрашивает ~100 полей, `usersGetFullExtended` — ~70; поля
   `mutual`, `counters.clips*`, `owner_state`, `stories_archive_count`, `buttons`,
   `profile_buttons`, `third_party_buttons`, `can_invite_to_chats`, `can_see_wishes` не
   запрашиваются — модели надо расширять вместе с fields.
4. **Серверные ограничения**: `al_payments.php`/`al_settings.php` — legacy web-POST с
   `hash`-токенами; прямой вызов из приложения ненадёжен (anti-bot), потому настройки PinoK
   правильно строит на BFF `settingsGeneral.*` — но покрытие ключей BFF неполное (нужно
   сверить список секций `getNotifySettings` с матрицей §1.4).
5. **i18n-якоря**: семейства ключей `privacy_options_*`, `settings_*_modal_aria_label`,
   `payments_*`, `nf_/sn_/nm_` — хороший чек-лист для приёмки UI (не забыть «Выбор друзей»,
   «Беззвучный режим», «Режим подписчиков», «Распознавание фото»).
