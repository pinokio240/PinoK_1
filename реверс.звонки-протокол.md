## 2. (d) Сигналинг: транспорт, команды, уведомления

### 2.1 Два транспорта
- WebSocket: wss://videowebrtc.okcdn.ru/ws2?userId=<uid>&entityType=USER&deviceIdx=0&conversationId=<call_id>&token=<tkn>&platform=WEB&appVersion=1.1&version=5&device=browser&capabilities=2F7F&clientType=VK&tgt=retry (kittenproxy/util/call.py:178)
- WebTransport (HTTP/3) — основной у веб-клиента: поле wt_endpoint; URL собирается как
  <wt_endpoint>&platform=WEB&appVersion=1.1&version=5&device=browser&capabilities=2F7F&clientType=VK&tgt=join&compression=deflate-raw
  (vk_joiner.go:392, main.go:562). Реализация: relay/wtsignal/wtsignal.go — QUIC+HTTP/3
  Extended CONNECT, proto-heder «webtransport», setting 0x2b603742 (ENABLE_WEBTRANSPORT draft-06),
  EnableDatagrams=false, keepAlive 15s; сообщения: quicvarint-длина + payload (deflate-raw при compression).
  **Именно WT-сигналинг даёт в ответе ноды transport «WEB_TRANSPORT»** (наблюдение PinoK).
  MAX-вариант: capabilities=603F, clientType=ONE_ME, tgt=start, Origin web.max.ru (maxcalls docs).

### 2.2 Кадр сообщений (JSON)
- Уведомления: {type:"notification", notification:"<name>", ...}:
  connection (conversationParams.stun/turn + conversation.participants + conversation.topology),
  settings-update, transmitted-data (participantId, data), registered-peer (participantId),
  topology-changed (topology), participant-joined/participant-added, participant-left,
  accepted-call (participantId), hungup, closed-conversation (reason).
- Ответы на команды: {type:"response", sequence:N}; ошибки: {type:"error", error:"...", message:"..."}.
- Команды (sequence начинается с 1, инкремент на каждую):
  * accept-call + mediaSettings {isAudioEnabled, isVideoEnabled, isScreenSharingEnabled,
    isFastScreenSharingEnabled, isAudioSharingEnabled, isAnimojiEnabled} (входящий принимает звонок)
  * transmit-data {participantId, participantType:"USER", data} — **весь SDP/ICE ходит через него**
  * change-media-settings {mediaSettings} (в т.ч. на лету: «mirroring how the web client
    toggles screenshare mid-call», main.go:341)
  * update-media-modifiers {mediaModifiers:{denoise:true, denoiseAnn:true}}
  * change-options {options:{FEEDBACK:true}} (kittenproxy)
  * remove-participant {participantId, ban:false} — кик «протухшего» пира при failed/disconnected (p2p.go:145)
  * get-rooms {withParticipants:false} (kittenproxy)
- ВАЖНО от whitelist-bypass (main.go:315): «VK SFU requires command, sequence, participantId
  before data» — в transmit-data поля строго в виде
  {"command":"transmit-data","sequence":N,"participantId":X,"data":{...}}.
- Пинг: сервер шлёт текст «ping» -> клиент обязан ответить текстом «pong» (все реализации).

### 2.3 Типовой порядок (по kittenproxy+maxcalls)
подключение -> notification connection (turn/stun/topology, participants)
-> [входящий] command accept-call
-> notification settings-update -> [исходящий] создают offer
-> command transmit-data {data:{sdp:{type:"offer",sdp}, animojiVersion:2}} / {data:{candidate:{...}}}
-> notification transmitted-data (answer / candidate от другого участника)
-> медиа в P2P (DIRECT) через полученные ICE-креды (host/srflx/relay)

transmitted-data.data для SDP: {"sdp":{"type":"answer","sdp":"v=0..."},"animojiVersion":2},
для ICE: {"candidate":{"candidate":"candidate:... udp ... typ host","sdpMid":"0","sdpMLineIndex":0}}
(kittenproxy wss.py:178; vk_joiner.go:708).

## 3. (e) САМОЕ ВАЖНОЕ: topology и мёртвая нода

### 3.1 Что известно о topology
- connection.conversation.topology — начальное значение («DIRECT» у работающих P2P).
- Уведомление topology-changed {topology:"SERVER"|...} — приходит при деградации.
- ЕДИНСТВЕННАЯ открытая обработка SERVER-топологии (обе версии в whitelist-bypass):
  // relay/pion/headless-joiner-common/vk_joiner.go:498
  case "topology-changed":
      topo, _ := msg["topology"].(string)
      if topo != "" && topo != vkTopologyDirect {
          h.logFn("vk-joiner: %s topology -> closing transport to reconnect and recover DIRECT", topo)
          h.closeTransport()   // ЗАКРЫТЬ WebTransport и ПЕРЕСОЕДИНИТЬСЯ целиком
      }
  и Bridge-версия (headless/vk/main.go:393): bounceForServerTopology -> закрыть SFU-транспорт ->
  внешний цикл (main.go:570) делает ПОЛНЫЙ rejoin: sleep 3s -> authAndJoin (новый session_key,
  новый endpoint/wt_endpoint, НОВЫЕ TURN-креды) -> новый PC -> новый offer. До 10 попыток
  (vkMaxReconnectAttempts), лимит bounce'ов, после которого подавляют screenshare.
- IceRestart/пересоздание offer на живой сессии при topology-changed НЕ ДЕЛАЕТ никто.
  Их философия: SERVER = сессия испорчена, восстанавливаемся полным rejoin'ом, пока не поймаем DIRECT.
- Причина SERVER-flap'ов по их опыту (main.go:341, 505): изменение числа треков
  (screenshare/dual-track) провоцирует SERVER; «suppressing screenshare to settle single-track DIRECT».

### 3.2 Почему у них «нода отвечает на ICE» (и при чём тут PinoK)
Во всех реализациях медиа-нода вообще НЕ медиа-пир: peer'ы — сами клиенты, ICE-связь
клиент<->клиент (DIRECT), ретрансляция — через TURN-серверы VK с кредами из §1. Медиа-нода
участвует только: (1) SFU-сигналинг (WS/WebTransport), (2) TURN-аллокация. Поэтому
«заставить ноду отвечать на connectivity checks» в открытых реализациях никто не делал —
вместо этого не дают звонку свалиться в SERVER:
1) свежие TURN-креды на каждое соединение (rejoin = новые креды!);
2) кандидаты другого пира добавляют и ДО setRemote, и после (буфер pendingICE — vk_joiner.go:720);
3) offer шлют ПОСЛЕ registered-peer/settings-update, кандидаты — после offer
   (sendOfferToPeer: сначала SDP, потом пачка кандидатов — p2p.go:175);
4) при failed/disconnected PC: remove-participant кик + rejoin (не ждут таймаутов сервера);
5) все три проекта шлют аудио-трек ВСЕГДА (даже когда данные идут через datachannel):
   kittenproxy — MediaPlayer("anullsrc=r=48000:cl=stereo") (тишина), whitelist-bypass —
   Opus TrackLocalStaticRTP + VP8 TrackLocalStaticSample. Звонок без аудио-трека аномален для протокола.
6) capability-строка веб-клиента capabilities=2F7F; «WEB_TRANSPORT» в логах PinoK — это
   транспорт СИГНАЛИНГА (wt_endpoint), не медиа.

Гипотеза для PinoK (из совокупности): SERVER-нога = медиа ноды через тот же ICE, где нода —
ICE-пир с парой host-кандидатов; открытых реализаций нет. Официальный клиент, скорее всего,
при topology-changed НЕ рестартит ICE, а переподключает сигналинг и ПЕРЕСОЗДАЁТ PC
С НОВЫМИ TURN-кредами (как whitelist-bypass, только внутри одного звонка). Проверить у PinoK:
(1) после topology-changed взять свежие turn/stun из conversationParams нового connection и
пересоздать PC целиком с ними; (2) перейти на wt_endpoint (WebTransport); (3) шлить offer
только после registered-peer, кандидаты — после offer; (4) аудио-трек sendrecv присутствует всегда.

### 3.3 «Credentials-модель» без SDP (maxcalls ICE) — важный нюанс
maxcalls (MAX) вообще не использует SDP: через transmit-data гоняет {UFrag, Password} и
кандидат-строки, затем pion/ice Dial(ufrag, pwd) — протокол допускает обмен ICE-кредами
напрямую (SDP — лишь обёртка). participantId берётся из ServerHello.conversation.participants[].id
(маппинг по externalId.id). Структуры: internal/api/signaling/messages/*.go; агент:
internal/ice/agent.go (pion/ice с WithUrls из stun_server/turn_server ответа).
