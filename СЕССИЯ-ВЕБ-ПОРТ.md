## 1. Как удерживается сессия в веб-версии (эталон)

### 1.1 Источник истины — cookie jar (не токены!)

| Cookie | Домен | TTL | Роль |
|---|---|---|---|
| `p` | .login.vk.ru | 1 год | Persistent login-token (`vk1.a.…`). По нему VK узнаёт юзера при ЛЮБОМ визите — вход без пароля/СМС |
| `remixsid` | .vk.ru/.vk.com | 1 год, ротейт | Классическая web-сессия; ротейтится при переходах (session rotation) |
| `remixstid` / `remixstlid` | .vk.ru | 1 год | `anonym_id` — постоянная анонимная идентичность (совпадает с JWT `auth.getAnonymToken`) |
| `sua` / `sui` | .login.vk.ru | 1 год | «Память о прошлой сессии» (user_id + старый токен); инвалидируется при новом логине |
| `httoken` | .login.vk.ru / .api.vk.ru | 1 нед | CSRF-token для login/api доменов |

### 1.2 Токены — одноразовые артефакты (24 ч)

localStorage ключи `<app_id>:…:login:auth`:
- `<app_id>:web_token:login:auth` → `{"access_token":"vk1.a.…","expires":+24h,"user_id":N,"logout_hash":"…"}`
- `<app_id>:get_anonym_token:login:auth` → anonym JWT (24 ч, работает даже без логина — FIX-133)
- `<app_id>:get_accounts:login:auth` → кеш аккаунтов

### 1.3 Механизм обновления — «перепосещение»

1. Любая загрузка vk.ru / id.vk.ru автоматически шлёт cookies.
2. VK видит живую `p`/`remixsid` → no_password_flow выдаёт auth code/silent_token БЕЗ ввода.
3. SPA обменивает на свежий web_token (24 ч) и кладёт в localStorage.
4. API-вызовы: `Authorization: Bearer vk1.a.…`.
5. Пароли/телефоны НИГДЕ не хранятся. Просрочился web_token → просто снова загрузили страницу.

**Суть: сессия = cookies; токены — 24-часовые производные.**

## 2. Что есть в PinoK сейчас (карта)

`auth/exchange/` (~9.2k строк) + AuthViewModel/OAuthWebViewActivity — ГИБРИД из 5+ путей:

| Путь | Файл | Суть | Веб-аналог |
|---|---|---|---|
| Логин WebView + web_token | `WebTokenAuth.kt` (1.6k) | WebView m.vk.ru → cookies → JS кладёт web_token в localStorage → читаем | ✅ ЭТО веб-механизм |
| Path 1.5 | `silentRefreshViaRemixsid` (в ExchangeAuthRepository, 7 стратегий) | HTTP-обновление по сохранённой копии remixsid | ❌ веб так не делает (он шлёт живые cookies) |
| Path 2.5 | trusted_hash re-login | Хранит `last_phone`+`last_password` в prefs | ❌ веб НЕ хранит пароль |
| Path 3 | exchange_token refresh | VK-SDK-паттерн | ❌ |
| Path 5 | connect_exchange_token (logout_hash) | VK ID web SDK | ❌ (частично) |
| Cookie-sync | `CookieRefreshWorker` + 3 хука (login/refresh/ON_RESUME) | CookieManager → storage раз в 6ч | ⚠️ нужен, но иначе (см. план) |
| Прочее | `ExternalBrowserAuth/Launcher`, `RemixsidCapturer`, `SilentTokenExchanger` | вспомогательные | ⚠️ по ситуации |

Проблемы гибрида: копия cookies в storage стейлится → мёртвые Path 1.5 при смене сети; храним пароль в prefs (безопасность); 5 путей = комбинаторика багов (см. #AUTH-LOOP-FIX, #SESSION-COOKIES-BG-REFRESH, auth.смена-сети).

## 3. Целевая архитектура (перенос веб-механизма 1:1)

**Принцип: CookieManager = единственный источник сессии; web_token = 24-часовой производный.**

1. **Логин** (уже есть): WebView VK ID → cookies в CookieManager (persist). Оставляем `WebTokenAuth` чтение localStorage.
2. **Refresh (замена всех путей)** — «перепосещение»:
   - триггеры: старт приложения / expires-24h / err=5 / смена сети;
   - скрытый WebView грузит `m.vk.ru` (или id.vk.ru auth-url) — живые cookies уходят сами;
   - VK молча выдаёт silent_token (window.init) / web_token (localStorage) — БЕЗ UI;
   - обменяли → токен в storage. Таймаут/неудача → только тогда показываем AuthActivity.
3. **Cookie-свежесть**: storage-копии cookies БОЛЬШЕ НЕ НУЖНЫ (никаких копий — источник живой). `CookieRefreshWorker`/backfill/hook'и — убрать.
4. **Fallback единственный**: если cookies мертвы (VK ответил «не залогинен») → полный логин. Как в вебе: просрочилась сессия → логин-страница.

## 4. Что убрать («остальное»)

- Path 1.5: `silentRefreshViaRemixsid` + 7 стратегий + `saveRemixsid`/`hasRemixsid`/`refreshSessionCookiesFromCookieManager`/backfill-хуки.
- Path 2.5: trusted_hash re-login + `KEY_LAST_PHONE`/`KEY_LAST_PASSWORD` (плюс: пароль больше не хранится на устройстве).
- Path 3: exchange_token refresh-ветку.
- Path 5: connect_exchange_token (logout_hash) — если не используется где-то ещё (проверить сервисы).
- `CookieRefreshWorker` + WorkManager-расписание.
- Из storage: копии cookies (remixsid/p/remixnsid), trusted_hash.
- `ExternalBrowserAuth` — обсудить: либо убрать, либо оставить как запасной вход.

## 5. Что сохранить

## 6. Риски / заметки

- Скрытый refresh медленнее HTTP (~1–3 c против ~200 мс) — делать lazy (не блокировать UI, кешировать по триггерам).
- WebView инициализация в фоне — аккуратно с main-thread.
- Смена сети больше не страшна: живые cookies уезжают с любого IP (как в вебе).
- VK ротейтит remixsid — нам неважно, мы копии не держим.
- Оценка: чистка ~2–3k строк, новый HiddenRefresh ~300–400 строк поверх WebTokenAuth.

## 8. #SESSION-WEB-EXPORT — следствие переноса (2026-09-24)

Перенос cookies в CookieManager сломал переносимость бэкапов: экспорт настроек
(SovaPrefsBackup) и account.json несли только storage-ключи — cookie jar (сама
web-сессия) терялся при переустановке/KeyStore-коррупции, восстановленный
access_token жил до первого refresh → пустой jar → ре-логин.

Решение — `auth/exchange/CookieJarBackup.kt`:
- снапшот: getCookie по `AuthDomainsConfig.vkCookieUrls()`, дедуп (домен, имя);
  домены выводятся по правилам §1 (getCookie атрибутов не отдаёт):
  `p` → .login.<base>, `remix*`/`httoken` → .<base>, прочие — host-only;
- импорт: setCookie с явным Domain/Path + flush;
- экспорт настроек: секция "cookies" в format=1 (формат не инкрементирован —
  секция опциональна, старые файлы совместимы; чекбокс «без сессии» убирает и её);
- account.json: поле `web_cookies` + заливка в restoreFromFileBackup;
- импорт старых файлов волн 45–52: фильтр мёртвых ключей секции session
  (last_phone/last_password/trusted_hash/копии cookies);
- VkCookieJar переведён на живой CookieManager (раньше читал стёртые
  storage-копии → пустой cookie-set на антифрод-эндпоинтах);
  исключение remixstid/remixstlid — #CALLS-ANTIFRAUD F-3.
