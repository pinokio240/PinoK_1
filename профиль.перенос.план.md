## §3. Архитектурные решения

1. **Профиль остаётся ядром** (рекомендация инвентаря §5.6, вариант а): ядерные `ProfileScreen`/
   `UserProfileScreen` развиваются напрямую, код юзера из «Контейнер Профиль» используется как
   **прототип UI** (идеи вкладок/рекомендаций), файлы контейнера не собираются в дерево сборки
   (хранятся в `upload/snapПрофиль/`, в git не переносятся до решения юзера).
   Вариант б (полная контейнеризация `:feature:profile` + `ProfileDependencies` по канону §3.2)
   — отдельное решение юзера после П-2; требует `git mv`, регистрации, хост-маппингов.
2. **Дефекты кода юзера** (при использовании прототипа): `photosGetAll` (метода нет — даст П-0),
   `AudioTrack`→`Track`, `online == true`→`online == 1`, `if (likesAdd(...))`→`> 0`,
   `List<Friend>`→`List<UserProfile>`; голые `Text`-заглушки вкладок запрещены политикой no-stub.
3. **Состояние профиля**: секции тянут данные через VKApiClient в стиле существующих экранов
   (loading/error/empty + рабочий «Повторить»); общие модели — расширение `UserProfile`
   (`:core:data`) по веб-набору полей (кластеры mutual/clips/buttons).
4. **Настройки**: приватность и уведомления — секции в `SettingsScreen` (host-маппинг capability),
   чёрный список — самостоятельная секция `settings_blacklist`.
5. **Позвонить** на чужом профиле — через `ContainerRegistry.find<CallStarter>()` (пattern шапки чата),
   с video-флагом после Этапа Б плана звонков.

## §4. Этапы внедрения

### П-0 — API-фундамент (без UI)
Все MISS-методы §2 → `VKApiClient` (`#PROFILE-SNAP (2026-09-…)`), стиль существующих блоков,
#NULL-EXPLICIT, #ANR-MAIN-IO. Расширить fields у `usersGetFullExtended` до веб-набора.
✅ Готовность: методы компилируются (самопроверка + kotlinc-harness как в А1), список методов
в KDoc-журнале; BuildStamp НЕ трогается.

### П-1 — Свой профиль
Обложка (отображение + «Изменить» → upload-цепочка обложки), вкладки контента
(`usersGetContentTabs` → переиспользование ядерных экранов Музыка/Видео/Фото),
подвкладки стены (`wallGetWithFilter`: главная/все/архив), «Действия» поста
(edit/delete/pin/unpin/spam), статус (`status.set`), правая колонка (друзья онлайн/подписчики/
подписки/подарки/клипы/статьи — каждая секция с real-API и empty-state).
✅ Готовность: матрица инвентаря §1.1 (строки профиля) чекается построчно.

### П-2 — Чужой профиль
Подписаться/Отписаться, Позвонить (CallStarter), Пожаловаться (`users.report`),
«Возможно, вы знакомы» (`friendsGetRecommendations`), подарки (`gifts.get`),
«Скопировать ссылку», «Скрыть из ленты» (`newsfeed.addBan/deleteBan`),
«В закладки» (`fave.addUser`), `friends.deleteSubscriber` (убрать подписчика).
✅ Готовность: матрица инвентаря §1.1 (чужой профиль) построчно.

### П-3 — Редактирование профиля
`account.getProfileInfo`/`saveProfileInfo` (имя/фамилия/статус/город/род занятий/…),
смена аватара (`photos.saveOwnerPhoto`-цепочка), обложка (upload-сервер + save/remove).
Самый тяжёлый этап — после П-1/П-2.
✅ Готовность: изменения реально сохраняются на сервере и видны после перезагрузки.

### П-4 — Настройки (4 страницы снапшота)
- Приватность: BFF `settingsGeneralGetPrivacySettings` → экран 6 секций; пункты-селекторы
  с исключениями «кроме N друзей» (друзья-пикер); запись через `settingsGeneralSetPrivacySettings`.
- Уведомления: довести NotificationSettingsScreen до матрицы инвентаря §1.4 (все ключи).
- Уведомления групп: секция 2×16 событий + управление источниками (включая «Удалить источник»).
- Чёрный список: вынести в `settings_blacklist` (список + добавление по ссылке/поиску + удаление).
- Голоса: экран-читалка баланса с честным empty-state «Платежи недоступны в клиенте» (web-only).
✅ Готовность: каждый переключатель/селектор читает и пишет реальное состояние.

### П-5 — Судьба «Контейнера Профиль» (решение юзера)
(а) код юзера остаётся прототипом, профиль — ядро (рекомендовано); (б) контейнеризация по §3.2.
В обоих вариантах 5 дефектов компиляции исправлены или файл закрыт.

### П-6 — No-stub приёмка
Построчный прогон матрицы инвентаря §1 (контрол → API → наблюдаемый эффект), лог со свежим
BuildStamp, `smartcast_hunt.py` по изменённым файлам, регресс профиля/настроек.

## §5. Риски

1. **Upload-цепочки** (аватар/обложка/фото поста) — многошаговые (getUploadServer → upload → save);
   реверс по бандлам обязателен перед П-1/П-3.
2. **Приватность-исключения** («кроме N») — веб делает через `al_friends.php` (web-only);
   нативный эквивалент требует подбора VK API-пути (проверить `account.setInfo`/BFF-варианты).
3. **Платежи (Голоса)** — web-only, нативно только чтение; не имитировать работу кнопок оплаты.
4. **Объём**: П-1/П-2 — основная трудоёмкость UI; П-0 — быстрый.

## §6. Порядок относительно других планов

Профиль не пересекается с очередью §3.7 (аудио) и с этапами Б–Е плана звонков
(разные файлы/модули). Этап П-0 может выполняться параллельно с Этапом Б звонков
(оба — только добавления в разные блоки `VKApiClient`; точки вставки разные).
