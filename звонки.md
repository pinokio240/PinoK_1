## 1. Executive Summary

VK-звонки (аудио/видео) организованы поверх **WebRTC** с собственным сигналингом.
Полный цикл звонка:

```
┌─────────────────────────────────────────────────────────────────────┐
│ 1. АВТОРИЗАЦИЯ CALLS-SDK                                            │
│    messages.getCallToken (VK API) → $-токен ($Ksd…)                 │
│      → auth.anonymLogin (calls.okcdn.ru) → session_key + okcdn uid  │
├─────────────────────────────────────────────────────────────────────┤
│ 2. СОЗДАНИЕ/ПОЛУЧЕНИЕ ЗВОНКА                                        │
│    Исходящий: messages.startCall → call_id → vchat.startConversation│
│    Входящий:  LP 115 (payload с conversation params)                │
│               → vchat.getConversationParams                         │
├─────────────────────────────────────────────────────────────────────┤
│ 3. СИГНАЛИНГ (два канала параллельно)                               │
│    • Long-poll queuev4.vk.ru/im1180 — события VK (LP 115 incoming)  │
│    • WebSocket wss://videowebrtc.okcdn.ru/ws2 — SDP/ICE обмен       │
├─────────────────────────────────────────────────────────────────────┤
│ 4. WEBRTC МЕДИА                                                     │
│    PeerConnection (STUN/TURN из conversation params, calls.okcdn.ru)│
│    Opus audio, DTLS-SRTP, ICE → CONNECTED → разговор                │
└─────────────────────────────────────────────────────────────────────┘
```

**Ключевые факты:**
- Два разных идентификатора: **VK user_id** (171093180) и **okcdn uid**
  (584520805550, из `auth.anonymLogin.uid`) — в WS-сигналинге используется okcdn uid.
- `conversation_id` для исходящего звонка — **UUID, генерируемый клиентом**
  (НЕ call_id из messages.startCall!). С call_id сервер закрывает conversation
  (`conversation-ended`, INITIALLY_CLOSED).
- API-хост calls: `https://calls.okcdn.ru/fb.do`, application_key
  `CGMMEJLGDIHBABABA` (web/MVK; OK-версия `CIOPGQJGDIHBABABA` даёт 210 DISABLED).
- В PinoK реализованы оба направления (входящий и исходящий) + UI + уведомления.

## 4. Авторизация vchat (общая для обоих направлений)

### 4.1. Цепочка (автоматическая, `SovaApp.ensureCallsSessionKey`)

```
1) messages.getCallToken (VK API, api.vk.com)          [VKApiClient.getCallToken]
   POST v=5.275, access_token=<vk1.a.*>, env=production
   Headers: Cookie=<remixsid/httoken…>, Origin=https://m.vk.ru,
            Referer=https://m.vk.ru/, UA=Chrome/Android 14 mobile,
            Sec-Fetch-*, Sec-Ch-Ua-*  (полный браузерный набор!)
   → { response: { token: "$Ksd…" } }   # $-токен, сохраняется в prefs.callsCallToken

2) auth.anonymLogin (calls.okcdn.ru/fb.do)             [VKApiClient.vchatAnonymLogin]
   method=auth.anonymLogin&format=JSON
   &application_key=CGMMEJLGDIHBABABA
   &session_data={"device_id":"<uuid>","client_version":"1.1",
                  "client_type":"SDK_JS","auth_token":"$Ksd…","version":3}
   → { session_key:"-w-fl…(156)", session_secret_key:"…", uid:584520805550, api_server:"…" }

3) Сохранение в prefs:
   callsSessionKey = session_key
   callsSessionUid = uid (okcdn!)  — для userId в WS URL
```

**Нюансы (проверено):**
- `client_version=1.1` (эталон Chrome desktop), не 2.0.0.
- `$Ksd…`-токен обязателен; `anonym.eyJ…` из `oauth.vk.ru/get_anonym_token`
  (client_id=7793118) сервер отвергает с 401 AUTH_LOGIN — метод getAnonymToken
  оставлен только как fallback.
- session_key протухает → `vchat.getConversationParams` отвечает 102
  PARAM_SESSION_EXPIRED → `getCallConversationParams` автоматически обновляет
  ключ (force) и повторяет запрос (до 2 попыток).

### 4.2. Fallback-перебор ключей

`ensureCallsSessionKey` перебирает application_key: `CGMMEJLGDIHBABABA` → `7793118` → `android_web` → `0`.

## 6. Long-poll очереди (queuev4) — канал событий VK

### 6.1. Запрос

```
GET https://queuev4.vk.ru/im1180?act=a_check&key=<key>&ts=<ts>&id=<uid>&wait=25
```
(`mode/version` НЕ передаются — mobile QueueManager формат; веб добавлял
`mode=202&version=10`, для двух-ts — `ts=<ts1>_<ts2>`)

### 6.2. Формат ответа

- Одна очередь: `{"ts":"1223912324","events":[]}` или `{"ts":"…","events":[[115,"<payload>"],…]}`
- Две очереди (параллельные): `[{"ts":"583705474","events":[]},{"ts":"1129989245","events":[]}]`
- Устаревший ts: `{"failed":2,"err":4}`
- events — массивы `[код, ...аргументы]`

### 6.3. LP-коды (Queuev4Client)

| Код | Константа | Значение | Payload |
|---|---|---|---|
| **115** | LP_INCOMING_CALL | Входящий звонок | `[115, "<len:base64 conversation params>"]` |
| **70** | LP_VIDEO_CALL | Видеозвонок | `[70, <userId>, "<callId>"]` |
| **-1** | LP_HISTORY_LOST | История потеряна | нужен ресинк/новый credential |
| **-2** | LP_KEY_EXPIRED | Ключ истёк | новый credential через queue.subscribe |

### 6.4. Очереди, которые держит PinoK

| Очередь | Подписка | Клиент | Назначение |
|---|---|---|---|
| `calls` | `queueSubscribe()` (без суффикса) | `queuev4Client` | входящие звонки (LP 115) |
| `nccts<uid>` | `queueSubscribe("nccts<uid>")` | `eventsQueuev4Client` | полные conversation params входящего |
| `events_queue<uid>` | `queueSubscribe("events_queue<uid>")` (fallback nccts) | `eventsQueuev4Client` | то же |
| manual | prefs `callsQueueKey/Ts` | `queuev4Client` | ручной credential из настроек |

Все три канала (`LongPollClient` 115 + queuev4 + events_queue) собираются в
`SovaApp.startCallNotifier()` — любое из событий показывает уведомление.

## 7. Conversation params (payload LP 115)

### 7.1. Формат payload

Строка вида `"<original_len>:<base64>"`:

```
1. split(":") → [original_len, base64]
2. base64 → байты
3. LZ4-декомпрессия (block format) → JSON-строка
4. JSON → { srcp, stne, tkn, trne, trnp, trnu, wse, wte }
```

### 7.2. Поля JSON → Params

| Поле JSON | В Params | Смысл |
|---|---|---|
| `tkn` | `token` | WS-токен сигналинга |
| `wse` | `endpoint` | wssBase (WebSocket signaling), напр. `wss://videowebrtc.okcdn.ru/ws2` |
| `wte` | `wtEndpoint` | WebTransport fallback |
| `stne` | `stunServer.urls` | STUN URL-ы (через запятую) |
| `trne` | `turnServer.urls` | TURN URL-ы (через запятую) |
| `trnu` | `turnServer.username` | TURN username |
| `trnp` | `turnServer.credential` | TURN password |

(`ConversationParamsDecoder.decode` — для payload; `decodeParamsJson` — для
JSON-ответа `vchat.getConversationParams` с полями id/endpoint/wtEndpoint/stun/turn/token/clientType/isConcurrent/device_idx)

### 7.3. LZ4 block format (реализация в PinoK)

Собственная реализация `lz4Decompress(src, expectedLen)`: токен-байт
(litLen 4 бита, продолжение 255), литералы, match (offset 2 байта LE,
matchLen 4 бита + 4, продолжение 255). Соответствует JS `_decodeExternalConversationParams`.

Особый случай: payload `"-1"` — параметров нет, их надо получить через
`messages.getCurrentCalls` → call_id → `vchat.getConversationParams`
(автоматическая цепочка в CallScreen).

### 8.4. Парсинг (CallSignalingClient.WsListener)

- command из `command` ИЛИ `notification`, иначе `detectCommand` по наличию

- Лог-маркеры: `FULL_CONNECTION`, `REGISTERED_PEER`, `REMOTE_HANGUP`,

### 9.3. RTCConfiguration (как в VK PeerConnectionClient.m109a)

```kotlin
sdpSemantics = UNIFIED_PLAN
continualGatheringPolicy = GATHER_CONTINUALLY
bundlePolicy = MAXBUNDLE
rtcpMuxPolicy = REQUIRE
tcpCandidatePolicy = ENABLED          // + TURN ?transport=tcp вариант

// pcConstraints.optional += DtlsSrtpKeyAgreement=true  ← без него нет DTLS
```

для каждого TURN без transport добавляется `?transport=tcp`-вариант
(не дублируя существующий `?transport=udp`). Fallback: `stun:videostun.okcdn.ru:19302`
+ `turn:calls.okcdn.ru:3478` (vk/vk).

### 9.4. Аудио

- Constraints: `googEchoCancellation=true, googNoiseSuppression=true,
  googAutoGainControl=true, googHighpassFilter=false` (как PeerConnectionAudioConstraints).
- Track `audio0`, stream `stream0`.
- `MODE_IN_COMMUNICATION` + AudioFocusRequest (USAGE_VOICE_COMMUNICATION,
  CONTENT_TYPE_SPEECH).
- Mute: `track.setEnabled(false)`; speaker: `AudioManager.isSpeakerphoneOn`.

### 9.5. SDP-обмен (порядок критичен!)

```
createOffer/Answer → setLocalDescription → onSetSuccess

Remote ICE до remoteDescription → pendingRemoteIce → drain после set
```

`OfferToReceiveAudio=true` + `OfferToReceiveVideo=true` (как VK; ответ на
audio-call содержит video m-line recvonly — это норма).

## 15. Критические подводные камни (проверено на практике)

1. **Без `JavaAudioDeviceModule` в factory** → нативный SIGABRT libjingle
   `front() called on an empty vector`. AudioDeviceModule создаётся ЯВНО
   и передаётся в builder (как в ru.ok.android.webrtc.SharedPeerConnectionFactory).
2. **Все операции PeerConnection — на signaling thread** (HandlerThread).
   createPeerConnection/createAudioSource с main-потока → тот же SIGABRT.
3. **createAnswer ТОЛЬКО в onSetSuccess** после setRemoteDescription
   (не сразу; SdpObserver: для set нужен `onSetSuccess`, НЕ `onCreateSuccess`).
   SDP отправлять только после setLocalDescription onSetSuccess.
4. **userId в WS URL = okcdn uid** (auth.anonymLogin.uid), НЕ VK user_id →
   иначе `invalid-token`.
5. **STUN/TURN только из conversation params** — хардкод videostun.okcdn.ru
   не даёт ICE CONNECTED (TURN credentials ротируются сервером; свежие
   приходят и в WS-событии `connection.conversationParams` — Chrome
   использует именно их).
6. **`conversation_id` в vchat — с подчёркиванием** (param `conversation_id`),
   а в startConversation/join/hangup — `conversationId`.
7. **Для исходящего conversation_id генерирует клиент (UUID)**, НЕ call_id
   из messages.startCall. С call_id сервер сразу `conversation-ended`
   (INITIALLY_CLOSED).
8. **`externalIds` вместо `uids`** в startConversation (эталон Chrome
   2026-08-24) + payload с caller_app_id + onlyAdminCanShareMovie.
9. **Дублирование transport в TURN URL** ломает сервер: склейка
   `"$url?transport=tcp"` при уже имеющемся `?transport=udp` даёт URL с двумя
   transport — libjingle молча отбрасывает сервер.
10. **Answer в исходящем звонке должен применяться сразу** (PC уже создан):
    если только кэшировать в pendingOffer (читается лишь кнопкой «Принять»
    входящего) — звонок вечно «Звоним…».
11. **okcdn uid нельзя хардкодить** — определение «это я» в
    connection.participants через `pId == 584520805550L` работало только на
    устройстве разработчика; на других offer уходил самому себе.
    uid берётся из prefs (`callsSessionUid`).
12. **RECORD_AUDIO обязателен ДО звонка**: без разрешения трек создаётся,
    но захват не идёт — собеседник слышит тишину.
13. **`$Ksd…`-токен обязателен для auth.anonymLogin (version=3)**:
    `anonym.eyJ…` из get_anonym_token даёт 401 AUTH_LOGIN; version=2 без
    auth_token даёт session_key формата `-w-vF…` (134), который vchat
    отвергает (100 must be specified).
14. **Инициатор тоже шлёт accept-call** после connection — иначе сервер
    не ретранслирует answer, звонок висит в CONNECTING.
15. **messages.startCall с web-токеном может быть не поддержан** — код
    ошибки показывается тостом («Звонки не поддерживаются для web-токена»).
16. **Только audio m-line** в offer — ответ содержит и video m-line (recvonly),
    это норма (CALLS_MAP §8.7).

## 19. Диагностика (logcat)

**Экранная диагностика (#CALLS-DIAG, 2026-08-29):** на CallScreen при
CONNECTING/FAILED/ENDED видны тех-строки — `Диагностика: WS <состояние> • PC
есть/нет • ICE <состояние>` и `Сигналинг: <последнее событие> • участник <id>`
(#CALLS-REOFFER: + `offer×N` — сколько раз переотправлялся offer; «offer×1»
после registered-peer = сработал фикс доставки). Скриншот экрана при неудачном
звонке даёт тот же ответ, что logcat: WS «ошибка:
…» → проблема сети/токена; WS «подключён» + «PC нет» → не дошли SDP; ICE
FAILED → сеть/TURN; «участник —» → не распознан собеседник в connection.

Включение CALLS-категории: `AppLog.setCategoryEnabled(LogCategory.CALLS, true)`
(выполняется автоматически в `startCallSignaling`).

| Тег | Что искать |
|---|---|
| `Queuev4Client` | `INCOMING_CALL (LP 115), payload.len=…`, `LP code -2 — credential expired` |
| `SovaApp` | `INCOMING_CALL (LP 115)`, `queue.subscribe OK (key=…)`, `ensureCallsSessionKey: OK (len=…, uid=…)`, `getCallParams: vchat OK` |
| `CallScreen` | `Incoming call, payload.len=…`, `Signaling start: conversationId=… userId=… (okUid=…)`, `Starting call to peerId=…`, `Call started: callId=…`, `applying remote answer immediately (PC ready)`, `participantId собеседника из connection.participants: …`, `Исходящий: отправляю accept-call`, `Собеседник завершил звонок`, `Исходящий: 45с без ответа`, `REOFFER #N (registered-peer/watchdog-20s): offer + N кандидатов → …`, `Watchdog: 60с в CONNECTING без answer` |
| `CallSignaling` | `onOpen: signaling connected`, `FULL_CONNECTION: …`, `REGISTERED_PEER: …`, `REMOTE_HANGUP: …`, `FULL_OFFER SDP`, `send: {command…}` |
| `WebRtcEngine` | `WebRTC initialized`, `Local audio track created`, `setIceServers: N servers`, `setRemoteSdp SUCCESS, pending=…`, `setLocalDescription(offer/answer) SUCCESS`, `ICE: CONNECTED/FAILED/DISCONNECTED`, `Remote audio track` |

Типовые ошибки: `invalid-token` (не тот userId в WS), `conversation-ended /
INITIALLY_CLOSED` (call_id вместо UUID), `102 PARAM_SESSION_EXPIRED` (ре renew
session_key), `100 PARAM_API_KEY / must be specified` (неверный ключ/формат
session_key), `401 AUTH_LOGIN` (не тот auth_token), `invalid-request`
(структура WS-команды), тишина у собеседника (RECORD_AUDIO).
