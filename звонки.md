## 1. Executive Summary

VK-звонки (аудио/видео) организованы поверх **WebRTC** с собственным сигналингом.
Полный цикл звонка:

```
┌─────────────────────────────────────────────────────────────────────┐
│ 1. АВТОРИЗАЦИЯ CALLS-SDK                                            │
│    messages.getCallToken (VK API) → $-токен ($Ksd…)                 │
│      → auth.anonymLogin (calls.okcdn.ru) → session_key + okcdn uid  │
├─────────────────────────────────────────────────────────────────────┤
│ 2. СОЗДАНИЕ/ПОЛУЧЕНИЕ ЗВОНКА                                        │
│    Исходящий: messages.startCall → call_id → vchat.startConversation│
│    Входящий:  LP 115 (payload с conversation params)                │
│               → vchat.getConversationParams                         │
├─────────────────────────────────────────────────────────────────────┤
│ 3. СИГНАЛИНГ (два канала параллельно)                               │
│    • Long-poll queuev4.vk.ru/im1180 — события VK (LP 115 incoming)  │
│    • WebSocket wss://videowebrtc.okcdn.ru/ws2 — SDP/ICE обмен       │
├─────────────────────────────────────────────────────────────────────┤
│ 4. WEBRTC МЕДИА                                                     │
│    PeerConnection (STUN/TURN из conversation params, calls.okcdn.ru)│
│    Opus audio, DTLS-SRTP, ICE → CONNECTED → разговор                │
└─────────────────────────────────────────────────────────────────────┘
```

**Ключевые факты:**
- Два разных идентификатора: **VK user_id** (171093180) и **okcdn uid**
  (584520805550, из `auth.anonymLogin.uid`) — в WS-сигналинге используется okcdn uid.
- `conversation_id` для исходящего звонка — **UUID, генерируемый клиентом**
  (НЕ call_id из messages.startCall!). С call_id сервер закрывает conversation
  (`conversation-ended`, INITIALLY_CLOSED).
- API-хост calls: `https://calls.okcdn.ru/fb.do`, application_key
  `CGMMEJLGDIHBABABA` (web/MVK; OK-версия `CIOPGQJGDIHBABABA` даёт 210 DISABLED).
- В PinoK реализованы оба направления (входящий и исходящий) + UI + уведомления.

## 4. Авторизация vchat (общая для обоих направлений)

### 4.1. Цепочка (автоматическая, `SovaApp.ensureCallsSessionKey`)

```
1) messages.getCallToken (VK API, api.vk.com)          [VKApiClient.getCallToken]
   POST v=5.275, access_token=<vk1.a.*>, env=production
   Headers: Cookie=<remixsid/httoken…>, Origin=https://m.vk.ru,
            Referer=https://m.vk.ru/, UA=Chrome/Android 14 mobile,
            Sec-Fetch-*, Sec-Ch-Ua-*  (полный браузерный набор!)
   → { response: { token: "$Ksd…" } }   # $-токен, сохраняется в prefs.callsCallToken

2) auth.anonymLogin (calls.okcdn.ru/fb.do)             [VKApiClient.vchatAnonymLogin]
   method=auth.anonymLogin&format=JSON
   &application_key=CGMMEJLGDIHBABABA
   &session_data={"device_id":"<uuid>","client_version":"1.1",
                  "client_type":"SDK_JS","auth_token":"$Ksd…","version":3}
   → { session_key:"-w-fl…(156)", session_secret_key:"…", uid:584520805550, api_server:"…" }

3) Сохранение в prefs:
   callsSessionKey = session_key
   callsSessionUid = uid (okcdn!)  — для userId в WS URL
```

**Нюансы (проверено):**
- `client_version=1.1` (эталон Chrome desktop), не 2.0.0.
- `$Ksd…`-токен обязателен; `anonym.eyJ…` из `oauth.vk.ru/get_anonym_token`
  (client_id=7793118) сервер отвергает с 401 AUTH_LOGIN — метод getAnonymToken
  оставлен только как fallback.
- session_key протухает → `vchat.getConversationParams` отвечает 102
  PARAM_SESSION_EXPIRED → `getCallConversationParams` автоматически обновляет
  ключ (force) и повторяет запрос (до 2 попыток).

### 4.2. Fallback-перебор ключей

`ensureCallsSessionKey` перебирает application_key: `CGMMEJLGDIHBABABA` → `7793118` → `android_web` → `0`.

## 6. Long-poll очереди (queuev4) — канал событий VK

### 6.1. Запрос

```
GET https://queuev4.vk.ru/im1180?act=a_check&key=<key>&ts=<ts>&id=<uid>&wait=25
```
(`mode/version` НЕ передаются — mobile QueueManager формат; веб добавлял
`mode=202&version=10`, для двух-ts — `ts=<ts1>_<ts2>`)

### 6.2. Формат ответа

- Одна очередь: `{"ts":"1223912324","events":[]}` или `{"ts":"…","events":[[115,"<payload>"],…]}`
- Две очереди (параллельные): `[{"ts":"583705474","events":[]},{"ts":"1129989245","events":[]}]`
- Устаревший ts: `{"failed":2,"err":4}`
- events — массивы `[код, ...аргументы]`

### 6.3. LP-коды (Queuev4Client)

| Код | Константа | Значение | Payload |
|---|---|---|---|
| **115** | LP_INCOMING_CALL | Входящий звонок | `[115, "<len:base64 conversation params>"]` |
| **70** | LP_VIDEO_CALL | Видеозвонок | `[70, <userId>, "<callId>"]` |
| **-1** | LP_HISTORY_LOST | История потеряна | нужен ресинк/новый credential |
| **-2** | LP_KEY_EXPIRED | Ключ истёк | новый credential через queue.subscribe |

### 6.4. Очереди, которые держит PinoK

| Очередь | Подписка | Клиент | Назначение |
|---|---|---|---|
| `calls` | `queueSubscribe()` (без суффикса) | `queuev4Client` | входящие звонки (LP 115) |
| `nccts<uid>` | `queueSubscribe("nccts<uid>")` | `eventsQueuev4Client` | полные conversation params входящего |
| `events_queue<uid>` | `queueSubscribe("events_queue<uid>")` (fallback nccts) | `eventsQueuev4Client` | то же |
| manual | prefs `callsQueueKey/Ts` | `queuev4Client` | ручной credential из настроек |

Все три канала (`LongPollClient` 115 + queuev4 + events_queue) собираются в
`SovaApp.startCallNotifier()` — любое из событий показывает уведомление.

## 7. Conversation params (payload LP 115)

### 7.1. Формат payload

Строка вида `"<original_len>:<base64>"`:

```
1. split(":") → [original_len, base64]
2. base64 → байты
3. LZ4-декомпрессия (block format) → JSON-строка
4. JSON → { srcp, stne, tkn, trne, trnp, trnu, wse, wte }
```

### 7.2. Поля JSON → Params

| Поле JSON | В Params | Смысл |
|---|---|---|
| `tkn` | `token` | WS-токен сигналинга |
| `wse` | `endpoint` | wssBase (WebSocket signaling), напр. `wss://videowebrtc.okcdn.ru/ws2` |

(`ConversationParamsDecoder.decode` — для payload; `decodeParamsJson` — для
JSON-ответа `vchat.getConversationParams` с полями id/endpoint/wtEndpoint/stun/turn/token/clientType/isConcurrent/device_idx)

### 7.3. LZ4 block format (реализация в PinoK)

Собственная реализация `lz4Decompress(src, expectedLen)`: токен-байт
(litLen 4 бита, продолжение 255), литералы, match (offset 2 байта LE,
matchLen 4 бита + 4, продолжение 255). Соответствует JS `_decodeExternalConversationParams`.

Особый случай: payload `"-1"` — параметров нет, их надо получить через
`messages.getCurrentCalls` → call_id → `vchat.getConversationParams`
(автоматическая цепочка в CallScreen).

### 8.3. Входящие уведомления

| notification / событие | Содержимое | Действие PinoK |
|---|---|---|
| `connection` | `{notification:"connection", peerId:{id,type:"WEB_SOCKET"}, endpoint, conversationParams:{turn,stun,…}, conversation:{participants:[{id, externalId:{id}, state}…]}}` | обновить ICE-серверы из conversationParams; вычислить remoteParticipantId из participants (не «я» = externalId.id != мой VK uid И id != мой okcdn uid); инициатор шлёт accept-call |
| `transmitted-data` с `data.sdp.type=offer` | `{notification:"transmitted-data", peerId:{id}, data:{sdp:{type:"offer",sdp:"…"}}}` | incoming: кэш до accept; PC создан → применить сразу |
| `transmitted-data` с `data.sdp.type=answer` | аналогично | PC создан → setRemoteSdp СРАЗУ (иначе «Звоним…» навсегда) |
| `transmitted-data` с `data.candidate` | ICE | PC есть → addIceCandidate; нет → кэш |
| `registered-peer` | `{notification:"registered-peer", participantId:<id>, participantType:"USER", peerId:{id,type}}` | participantId — куда слать offer/ICE (исходящий); **переотправить offer + все локальные кандидаты** (#CALLS-REOFFER: сервер выбрасывает transmit-data, отправленный ДО registered-peer — у собеседника ещё нет активного WS-peer'а; переотправка на КАЖДЫЙ registered-peer, пока нет answer) |
| `accepted-call` | `{notification:"accepted-call", participantId?}` | собеседник ПРИНЯЛ звонок (#CALLS-ACK-REOFFER, 2026-08-29): единственный гарантированный момент, когда вызываемый готов принимать transmit-data (лог 20:31: registered-peer 25.316 → accepted-call 32.487). **Переотправить offer ещё раз** (guard answerReceived); если remoteParticipantId ещё не известен — взять из participantId |
| `topology-changed` | `{topology:"DIRECT"\|"SERVER", offerTo:[<participantId>]}` | повторно отправить offer + кандидаты новому адресату (кэш или engine.lastLocalSdp) |
| `response` | `{type:"response", sequence:N, response:"accept-call"\|"transmit-data", participantIds:[]}` | ack: ЛОГИРУЕТСЯ на INFO + diag «ack:…» (#CALLS-ACK-REOFFER: participantIds — кому реально доставлен transmit-data); `type:"error"` → diag «ошибка сервера» |
| `{data:{sdp:"v=0…", type:"offer"}}` (sdp — СТРОКА, не объект) | вариант envelope | #CALLS-ACK-REOFFER: detectCommand распознаёт примитивный sdp (раньше классифицировался «event» и терялся) |
| `hangup` / `hungup` / `call-ended` / `conversation-ended` / `closed-conversation` / `closed` / `ended` / `participant-left` / `participant-removed` / `call-rejected` / `rejected` | — | маппятся в CMD_REMOTE_HANGUP → ENDED |
| `{stamp, error:"invalid-request", message}` | ошибка | FAILED |

### 8.4. Парсинг (CallSignalingClient.WsListener)

- command из `command` ИЛИ `notification`, иначе `detectCommand` по наличию
  sdp/candidate (`transmitted-data`/`data`/`event` → detect).
- SDP вкладывается по-разному (`data.sdp.sdp.sdp`, `data.sdp.sdp`,
  `sdp.sdp`) — parseSdp обходит все варианты; participantId из `participantId`
  или `peerId.id`.
- Лог-маркеры: `FULL_CONNECTION`, `REGISTERED_PEER`, `REMOTE_HANGUP`,
  `FULL_OFFER SDP`, `FULL_ANSWER SDP`.

### 9.2. PeerConnectionFactory (инициализация на своём signaling thread)

### 9.3. RTCConfiguration (как в VK PeerConnectionClient.m109a)

```kotlin
sdpSemantics = UNIFIED_PLAN
continualGatheringPolicy = GATHER_CONTINUALLY
bundlePolicy = MAXBUNDLE
rtcpMuxPolicy = REQUIRE
tcpCandidatePolicy = ENABLED          // + TURN ?transport=tcp вариант
keyType = ECDSA
iceTransportsType = ALL
// pcConstraints.optional += DtlsSrtpKeyAgreement=true  ← без него нет DTLS
```

ICE-серверы: из conversation params (stun/turn с username/credential);
для каждого TURN без transport добавляется `?transport=tcp`-вариант
(не дублируя существующий `?transport=udp`). Fallback: `stun:videostun.okcdn.ru:19302`
+ `turn:calls.okcdn.ru:3478` (vk/vk).

### 9.4. Аудио

- Constraints: `googEchoCancellation=true, googNoiseSuppression=true,
  googAutoGainControl=true, googHighpassFilter=false` (как PeerConnectionAudioConstraints).
- Track `audio0`, stream `stream0`.
- `MODE_IN_COMMUNICATION` + AudioFocusRequest (USAGE_VOICE_COMMUNICATION,
  CONTENT_TYPE_SPEECH).
- Mute: `track.setEnabled(false)`; speaker: `AudioManager.isSpeakerphoneOn`.

### 9.5. SDP-обмен (порядок критичен!)

```
createOffer/Answer → setLocalDescription → onSetSuccess
  → lastLocalSdp = sdp; onLocalSdpReady(sdp)      ← отправка ТОЛЬКО здесь
setRemoteSdp(offer) → onSetSuccess → createAnswer() ← answer СТРОГО тут
Remote ICE до remoteDescription → pendingRemoteIce → drain после set
```

`OfferToReceiveAudio=true` + `OfferToReceiveVideo=true` (как VK; ответ на
audio-call содержит video m-line recvonly — это норма).

## 15. Критические подводные камни (проверено на практике)

1. **Без `JavaAudioDeviceModule` в factory** → нативный SIGABRT libjingle
   `front() called on an empty vector`. AudioDeviceModule создаётся ЯВНО
   и передаётся в builder (как в ru.ok.android.webrtc.SharedPeerConnectionFactory).
2. **Все операции PeerConnection — на signaling thread** (HandlerThread).
   createPeerConnection/createAudioSource с main-потока → тот же SIGABRT.
3. **createAnswer ТОЛЬКО в onSetSuccess** после setRemoteDescription
   (не сразу; SdpObserver: для set нужен `onSetSuccess`, НЕ `onCreateSuccess`).
   SDP отправлять только после setLocalDescription onSetSuccess.
4. **userId в WS URL = okcdn uid** (auth.anonymLogin.uid), НЕ VK user_id →
   иначе `invalid-token`.
5. **STUN/TURN только из conversation params** — хардкод videostun.okcdn.ru
   не даёт ICE CONNECTED (TURN credentials ротируются сервером; свежие
   приходят и в WS-событии `connection.conversationParams` — Chrome
   использует именно их).
6. **`conversation_id` в vchat — с подчёркиванием** (param `conversation_id`),
   а в startConversation/join/hangup — `conversationId`.
7. **Для исходящего conversation_id генерирует клиент (UUID)**, НЕ call_id
   из messages.startCall. С call_id сервер сразу `conversation-ended`
   (INITIALLY_CLOSED).
8. **`externalIds` вместо `uids`** в startConversation (эталон Chrome
   2026-08-24) + payload с caller_app_id + onlyAdminCanShareMovie.
9. **Дублирование transport в TURN URL** ломает сервер: склейка
   `"$url?transport=tcp"` при уже имеющемся `?transport=udp` даёт URL с двумя
   transport — libjingle молча отбрасывает сервер.
10. **Answer в исходящем звонке должен применяться сразу** (PC уже создан):
    если только кэшировать в pendingOffer (читается лишь кнопкой «Принять»
    входящего) — звонок вечно «Звоним…».
11. **okcdn uid нельзя хардкодить** — определение «это я» в
    connection.participants через `pId == 584520805550L` работало только на
    устройстве разработчика; на других offer уходил самому себе.
    uid берётся из prefs (`callsSessionUid`).
12. **RECORD_AUDIO обязателен ДО звонка**: без разрешения трек создаётся,
    но захват не идёт — собеседник слышит тишину.
13. **`$Ksd…`-токен обязателен для auth.anonymLogin (version=3)**:
    `anonym.eyJ…` из get_anonym_token даёт 401 AUTH_LOGIN; version=2 без
    auth_token даёт session_key формата `-w-vF…` (134), который vchat
    отвергает (100 must be specified).
14. **Инициатор тоже шлёт accept-call** после connection — иначе сервер
    не ретранслирует answer, звонок висит в CONNECTING.
15. **messages.startCall с web-токеном может быть не поддержан** — код
    ошибки показывается тостом («Звонки не поддерживаются для web-токена»).
16. **Только audio m-line** в offer — ответ содержит и video m-line (recvonly),
    это норма (CALLS_MAP §8.7).
17. **Кэш offer нельзя читать в кнопке «Принять»** (#CALLS-IN-OFFER, лог 21:26):
    offer прилетает в любой момент до/во время accept — кэш, прочитанный ПОСЛЕ
    engine.acceptCall и затёртый (`pendingOffer.value = null`), терял offer,
    answer не создавался, звонящий повисал и сбрасывал звонок (~37с,
    remote-hangup). Теперь remote SDP/ICE буферизует сам движок
    (WebRtcEngine.pendingRemoteSdp) и применяет сразу после создания PC —
    гонка UI устранена по построению.
18. **queuev4-события менять фазу входящего нельзя** (#CALLS-IN-OFFER):
    queuev4Client остаётся подписан на очередь «calls» после исходящего и при
    входящем получает то же LP 115 — фаза прыгала RINGING→CONNECTING без
    «Принять» (экран «Соединение…» без кнопок). Гейт: только для OUTGOING.

## 20. Входящий звонок: цепочка и грабли (#CALLS-IN-FIX, 2026-08-29)

**Лог 20:54 (входящий):** INCOMING_CALL (LP 115, payload="-1") → vchat.getConversationParams
ВИСЕЛ 45с (readTimeout клиента рассчитан на long-poll) → сигналинг не поднялся
(нет ни setIceServers, ни connectLoop) → пользователь нажал «Принять» вхолостую
(accept-call ушёл в никуда) → 37с «Соединение…» → ICE: CLOSED.

**Фиксы:**
1. VKApiClient.vchatGetConversationParams: КАЖДЫЙ HTTP-вызов ограничен 10с
   (`call.timeout().timeout(10s)`) — общий readTimeout 45с для vchat не годится.
2. SovaApp.getCallConversationParams: null-результат attempt'а ЛОГИРУЕТСЯ
   (`getCallParams: vchat null (attempt N, convId=…)`) — раньше тишина.
3. CallScreen «Принять»: ждёт params (CompletableDeferred, ≤20с) → поднимает
   сигналинг, если ещё не поднят → ждёт открытия WS (≤10с, isWsReady()) →
   vchatJoinConversation → engine.acceptCall → применить offer/кандидаты →
   signaling.acceptCall. Ошибки → FAILED с текстом на экране.
4. CallScreen «Отклонить»: если WS не готов — HTTP-fallback

5. CallSignalingClient.isWsReady() — public-проверка «команды уходят».

### 20.1. Продолжение: звонящий сам сбрасывал звонок (#CALLS-IN-OFFER, 2026-08-29)

**Скриншот 21:26 (входящий):** «Звонок завершён», диагностика
`WS выкл • PC нет • ICE CLOSED`, сигналинг `remote-hangup • участник
595859469344`. PC существовал (ICE CLOSED — из endCall) → «Принять» было
нажато, но звонящий сбросил через ~37с сам.

**Причины (устранены все):**
1. **Гонка кэша offer:** offer кэшировался в UI (`pendingOffer`) и читался
   ТОЛЬКО кнопкой «Принять» — ПОСЛЕ `engine.acceptCall`. Offer, прилетевший
   в момент нажатия, затирался (`pendingOffer.value = null`) → answer не
   создавался вовсе → звонящий повисал и сбрасывал. Теперь remote SDP/ICE
   буферизует сам WebRtcEngine (pendingRemoteSdp + уже бывший pendingRemoteIce)
   и применяет сразу после создания PC — UI-кэша больше нет.
2. **Пустой conversationId в WS:** call_id доставался только когда payload="-1";
   если payload содержал params (events_queue), WS уходил с `conversationId=`
   (пусто) — registered-peer звонящему мог не уйти, его offer до нас не доходил.
   Теперь messages.getCurrentCalls вызывается ВСЕГДА.
3. **Нет watchdog'а входящего CONNECTING:** при потере offer — вечное
   «Соединение…» до remote-hangup. Теперь 8с → nudge (перерегистрация WS →
   registered-peer звонящему → он переотправит offer), 45с → FAILED
   «Данные звонка не получены (offer не пришёл)».
4. **Ловушка queuev4:** после исходящего звонка клиент остаётся подписан на
   очередь «calls» и при входящем получает то же LP 115 — фаза прыгала
   RINGING→CONNECTING без «Принять». Гейт: только OUTGOING.
5. Diag дополнена `offer ✓/— • answer ✓/—` — следующий скриншот однозначно
   покажет, на каком звене обрыв.

**Признак в логе, что params висят:** `getCallParams: session_key из prefs`
без последующего `vchat OK` / `vchat null` дольше 10с = сеть/сервер держит
запрос; после фикса попытка рвётся на 10-й секунде и видна в логе.

   гарантированный момент его готовности к transmit-data. В логе 20:31
   registered-peer был в 25.316, accepted-call — в 32.487 (7с между ними):
   если сервер ретранслирует transmit-data только «принявшим» peer'ам, наш
   reoffer на registered-peer тоже выбрасывался. Теперь: reoffer и на
   accepted-call (guard answerReceived).
2. **answer терялся молча.** `send()` при закрытом WS отбрасывал команду,
   но `answerSent` уже стоял true; ретраев не было. Теперь send()→Boolean,
   `sendAnswerReliably`: ретрай каждые 500мс до 15с, answerSent — только на
   успехе; diag `answer×N`.
3. **Offer без participantId блокировал answer навсегда.** Если offer пришёл
   без pid, созданный answer кэшировался и не отправлялся никогда. Теперь
   `flushPendingLocal(pid)` — флаш кэша при первом появлении participantId
   (из candidates / connection.participants / accepted-call).
4. **Порядок accept/answer.** В «Принять» accept-call уходит ДО
   engine.acceptCall — детерминированно раньше answer (сервер может
   ретранслировать transmit-data только подтвердившим участие).
5. **Nudge без re-accept.** Перерегистрация WS создавала нового peer'а, о
   котором сервер мог знать «не принявшим». Теперь nudge после
   перерегистрации отправляет accept-call повторно; добавлен RINGING-nudge

6. **DISCONNECTED рвал живые звонки.** Первый же ICE DISCONNECTED переводил
   экран в ENDED. Теперь grace 10с (CONNECTED отменяет таймер) —
   транзиентные пропадания сети не обрывают разговор (#CALLS-DROP-GRACE).
7. **Слепые зоны диагностики.** ack'и сервера (type:response/error) теперь
   логируются на INFO (`SERVER_RESPONSE: …`) + diag «ack:…»;

   примитивный sdp-энвелоп (data.sdp строкой); тег CallSignaling отнесён к
   категории CALLS; в diag добавлены `conv ✓/—` и `answer×N`.

## §21. «У звонящего таймер идёт, а PinoK не поднимает трубку» (#CALLS-ICE-WATCHDOG, 2026-08-29)

**Симптом после 59391ed (doReanswer уже в сборке):** у звонящего (VK Desktop)
таймер разговора УЖЕ ИДЁТ, а PinoK «не поднимает трубку» — экран не доходит
до ACTIVE (таймера на PinoK нет, «Соединение…»).

**Разбор (что это значит):**
1. Таймер у звонящего стартует, когда сервер считает звонок отвечённым:
   наш accept УШЁЛ (vchat.joinConversation + WS accept-call) — кнопка
   «Принять» и сигналинг РАБОТАЮТ. doReanswer из 59391ed тоже сработал:
   раньше звонящий сбрасывал через 40с без таймера, теперь он «в звонке».
2. «Не поднимает трубку» = МЕДИА (ICE) на нашей стороне не дошло до
   CONNECTED → phase != ACTIVE. Т.е. остаточная проблема — чисто ICE.
3. **Доказанная дыра:** для состояния «answer отправлен, ICE не подключился»
   НЕ БЫЛО НИКАКОГО таймаута (IN-Watchdog на 45с убивал звонок только при
   `!answerSent`). Звонок висел «Соединение…» вечно; звонящий — со своим
   таймером навсегда (никто не клал трубку с обеих сторон).

**Фиксы (#CALLS-ICE-WATCHDOG):**
1. **ICE-Watchdog (CallScreen, входящий, key = phase+answerSent):**
   +15с после отправки answer без ICE → dumpIceStatsNow + doReanswer;
   +35с → повторный doReanswer; +60с → сами кладём трубку (hangup "timeout")
   с failText «Медиа-соединение не установлено (ICE)» — у звонящего таймер
   наконец останавливается.
2. **Восстановление при ICE FAILED (входящий, answer отправлен):** до 2
   попыток — doReanswer("ice-failed") + возврат в CONNECTING (reanswer
   заставляет собеседника пересобрать соединение: его проверки доходят до
   нашего relay → пары валидируются). Исчерпаны → hangup (звонящий не висит).
3. **failText на engine-FAILED** — вместо безликого «Ошибка соединения»
   показывается причина («Медиа-соединение не установлено (ICE)»).
4. **dumpIceStatsNow (WebRtcEngine)** — публичный обёртка dumpIceStats:
   снимок candidate-pair по требованию watchdog'ов (не только при FAILED).
5. **TURN TCP-fallback (WebRtcEngine.setIceServers):** для URL с
   `?transport=udp` теперь добавляется TCP-вариант ТОГО ЖЕ сервера
   (replace udp→tcp) — как в Chrome (udp+tcp пара на 3478). Раньше URL с
   transport= пропускался целиком — TCP-fallback не добавлялся вовсе; на
   LTE/за жёстким NAT (UDP режется) ICE умирал в CHECKING→FAILED.

**Что смотреть в следующем логе (решающий диагноз по ICE stats):**
- `reqS>0, resR=0, reqR=0` — наши проверки уходят, собеседник молчит
  (answer снова не применён у него) → проблема на его стороне/сети;
- `reqR>0` — его проверки ДОХОДЯТ до нас — проблема в наших ответах/аллокации;
- появление `relay …tcp` кандидатов — TCP-fallback задействован.
Экранные маркеры: `ans×N` (reanswer-счётчик), failText «Медиа-соединение не
установлено (ICE)» максимум через ~60с после answer (больше вечных «Соединение…»).

   сервера (type:"error") обрабатывались чисто косметически (diagEvent), звонок

   (данные не доставляются)». На diag добавлен `err×N`.
2. **Гвард FAILED-retry:** при srvErrCount≥2 ретраи запрещены (иначе retry

3. **Поллинг-сторож зомби (1с):** (а) CONNECTING без PC ≥3с → терминалим

4. **CallSignalingClient:** алиасы завершения расширены (conversation-closed,
   call-closed, cancelled/canceled, participant-leaved, left, declined/decline…);
   нераспознанные уведомления подняты с DEBUG на INFO — следующий лог покажет
   точное имя незаматченного hangup-уведомления.

**Инвариант после фикса:** зомби-CONNECTING невозможен — любое мёртвое
состояние терминализируется максимум за 3с (PC нет) / 90с (абсолютный дедлайн),

**Фиксы (#CALLS-RX-DEBUG):**
1. **Строка «Принято:»** (CallScreen): счётчик ВСЕХ входящих команд

   connection×1…`. Нет «candidate» при живом WS = собеседник не шлёт
   кандидаты (или шлёт в другом формате — см. `onMessage` в логе).
2. **«прин:N sdpR:+/-»** в строке «Медиа:» (WebRtcEngine.remoteCandCount +
   hasRemoteDescription): принятые удалённые кандидаты и применён ли
   удалённый SDP. `пар=0 • прин:0` = кандидатов не приходило ВОВСЕ;

   смотреть `addRemoteIceCandidate` в логе).
3. **diag-блок теперь виден и в RINGING** (раньше прятался — а там важен
   nudge/отсутствие offer); поллинг «Медиа:» тоже обновляется в RINGING.

**Шпаргалка дополнение:**
- `пар=0 • прин:0` (sdpR:+) → удалённых кандидатов нет: либо собеседник их
  не шлёт, либо шлёт командой, которую мы не мапим (смотреть «Принято:» и
  `onMessage: command=… eff=…` INFO-лог — точное имя пропустит);
- `пар=0 • прин:N (N>0)` → кандидаты пришли, но не в пары — смотреть
  `addRemoteIceCandidate PENDING/OK` и дренаж буфера.
