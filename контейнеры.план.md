## ЧАСТЬ 1 — Контейнеризация (модульная архитектура разделов)

Идея: каждый раздел приложения (звонки, фото, аудио, …) — самостоятельный
Gradle-модуль-«контейнер», который экспортирует **capability** (навигацию,
настройки, рендеры вложений) в общий реестр. Хост строит UI из реестра.
Контейнер можно добавить/удалить **без потери функций остального приложения**:
нет контейнера → нет пункта меню/настройки/кнопки, ядро не падает
(например, чат при удалённом `photos` показывает заглушку «скачать файл»).

Правила зависимостей (зафиксированы в KDoc `:contracts`):
- `:feature:*` зависят **только** от `:contracts` + `:core:*`;
  друг от друга — НИКОГДА.
- Состояние контейнера изолировано (свои таблицы/префы/подкаталоги кэша).
- Хост строит UI из `ContainerRegistry.find<T>()`, graceful-деградация везде.
- Контракты (`:contracts`) — БЕЗ androidx/compose: минимальная поверхность
  (иконки мапит хост по `iconKey`, не модуль).

### Правило владения UI (решение пользователя 2026-09-01 — ЗАФИКСИРОВАНО)

- **Ядро (`:app`) владеет НАВСЕГДА** (не зависит от контейнеров):
  - оболочка боковой панели (drawer) и Dock (лента/сообщения/музыка/видео/профиль);
  - экран **Настроек** как таковой — общие ядерные вкладки (интерфейс, сеть,
    уведомления, приватность, безопасность…);
  - пункт **Выход**.
- **Контейнер экспортирует два UI-capability**, которые появляются ТОЛЬКО пока
  контейнер зарегистрирован в `ContainerRegistry`:
  - `NavEntry` → кнопка в боковой панели с названием контейнера;
  - `SettingsSection` → своя вкладка в Настройках (динамически добавляется
    в `PrimaryScrollableTabRow` после ядерных, сортировка по `order`).
- Подключили контейнер → кнопка на панели + вкладка в настройках появились
  сами; убрали контейнер из реестра → оба исчезли, ядро (чат, настройки, выход)
  живо без изменений.
- Где сейчас живёт то, что переведём на реестр (Этап 1.4):
  - пункты панели — `Screen` (`ui/navigation/Screen.kt`) + drawer в `SovaNavHost.kt`
    (захардкожено);
  - вкладки настроек — `SettingsTab` enum в `SettingsScreen.kt`
    (`PrimaryScrollableTabRow` + `HorizontalPager`).
- Реестр пуст (сейчас) → панель и настройки показывают только ядерные пункты.

### 3.1. Термины и два канала связи

- **Ядро** — `:app`: единственный владелец рантайм-объектов (SovaApp, VKApiClient,
  LongPoll/Queue-клиенты, ExchangeAuthRepository), навигации (NavHost), Service/PendingIntent/R.
- **Контейнер** — `:feature:*`: экраны + своя логика. Декларирует, ЧТО ему нужно;
  не знает, ОТКУДА это приходит. Добавление/удаление не ломает ядро (graceful).
- **Композиционный корень** — единственное место сборки: `SovaApp.onCreate`
  (init + регистрация) и `MainActivity.setContent` (провайдер зависимостей).
- **Порт (хост-хук)** — интерфейс в `:contracts`, который контейнер ВЫЗЫВАЕТ у ядра (`CallStarter`).
- **Фасад** — интерфейс, объявленный В контейнере, который ядро РЕАЛИЗУЕТ (`CallsApi`).
- **Host-маппинг** — статические switch'и ядра: route→Screen, iconKey→Icons,
  settings-route→компосабл, rendererKey→рендер.

Схема зависимостей (стрелки ТОЛЬКО вниз; `:feature → :app` запрещён Gradle
— цикл — и дизайном):

```
:app (ядро, композиционный корень)
 ├──► :feature:calls / photos / audio      (контейнеры)
 │         ├──► :contracts (порты хоста; БЕЗ androidx/compose)
 │         └──► :core:common / network / media / data
 └──► :contracts, :core:*
```

| Канал | Кто инициатор | Механизм | Где живёт контракт |
|---|---|---|---|
| Зависимости (контейнеру нужны объекты ядра) | контейнер | `XxxDependencies` + фасады + `LocalXxxDeps` (staticCompositionLocalOf, fail-fast) | В САМОМ контейнере |
| Хост-хуки (ядро/контейнер просит ядро) | ядро ↔ контейнер | capability через `ContainerRegistry.find<T>()` (`CallStarter`, `NavEntry`, `SettingsSection`, `AttachmentRenderer`, `PermissionNeeds`) | `:contracts` |

### 3.5. Инварианты независимости контейнера от ядра (проверяемые)

- **И1 — импорты**: в `:feature:Xxx` нет `import re.pinok.*` из пакетов :app (grep).
- **И2 — gradle**: в `feature/xxx/build.gradle.kts` нет `project(":app")`;
  `:contracts` без androidx/compose (по build.gradle.kts).
- **И3 — полнота**: все члены `XxxDependencies` реализованы в :app;
  census вызовов = фасадам 100% (обе стороны).
- **И4 — рантайм-честность**: фасад не создаёт новых объектов — те же синглтоны ядра.
- **И5 — fail-fast**: `LocalXxxDeps` без провайдера падает при композиции
  (не глотается catch — паттерн Task 22 запрещён).
- **И6 — graceful**: «регистрация закомментирована» → ядро живо, capability исчезают
  (ментальный эксперимент 1.4/1.5).
- **И7 — гигиена**: NULL-EXPLICIT + оба сканера чисты до передачи на сборку.

### 3.6. Ловушки (проверено на своих граблях)

1. **kotlin.compose без compose-runtime** = `IrGenerationExtensionException` на
   fir2ir-фазе (Task 18) — плагин ставится ТОЛЬКО вместе с набором compose.
2. **Same-package слепая зона**: same-package ссылки не требуют import — анализ
   переносимости по ВСЕМ ссылкам пакета, не только по import (Task 21: 330 ошибок одним файлом).
3. **Дефолты в override запрещены Kotlin** — дефолт живёт в интерфейсе, override
   без дефолтов (Task 22-комментарий «легален» был ошибочен; исправлено
   `783463ae`/`b5d0f153`/`197819a6`).
4. **`LocalXxxDeps.current` — читать ТОЛЬКО на compose-уровне**, не внутри try
   внутри LaunchedEffect/DisposableEffect (K2 запрещает оба паттерна; Task 22).
5. **Блочные комментарии Kotlin ВКЛАДЫВАЮТСЯ**: `/**` внутри открытого KDoc глотает
   код до EOF (Task 23: 42 ошибки одной строкой, `bb3e3e55`) — проверять
   комментарий-сканером, скобочный баланс не ловит.
6. **Фасад не меняет рантайм**: возврат :app-типов из фасада = ошибка (откат
   `aff1327e`); расширение фасада — только по census фактических вызовов
   (танцы `f89efb64`→`1c85a559`).
7. **Межмодульный смарт-каст невозможен** (K1/K2, Этап 3.7-1): после переноса
   типов в модуль (data.model → :core:data) public API property другого модуля
   НЕ смарт-кастится после null-проверки — до переноса модели и потребители
   жили в одном :app, касты были легальны. Паттерн фикса: захват в локальный
   `val` + явная проверка (`isNullOrBlank()`/`!= null` смарт-кастит локальный
   val; ограничение «чужой модуль» на него не действует; захват легален и в
   `item{}`-лямбды LazyColumn — val иммутабелен). Вторая форма — second-order
   инференс: локальный val из if/when-ветки выводит `String?`/`T?` (ветка
   потеряла каст) и падает ниже (`isNotBlank`/`contains` на nullable receiver).
   При переносе типов смарт-касты всплывают и в ОБРАТНУЮ сторону (ядро —
   потребитель фичевого типа). Инструмент: `.zscripts/smartcast_hunt.py`
   (39 nullable backing-val свойств моделей × check→use окно 25 строк /
   SAME-LINE / when-else) — гонять на Этапе Д каждого переноса типов
   (волны 3.7-1: `b4726c7f` 17 точек в 8 файлах, `a1c0d8ae` 30 точек в 12 файлах).
