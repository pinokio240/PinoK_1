## 1. Диагноз

### 1.1 Краш-векторы («приложение может закрыться»)

Механика одна: **дубликаты ключей в Lazy-контейнерах Compose**.
`LazyColumn`/`LazyRow` с `items(list, key = { … })` бросает
`IllegalArgumentException: Key "…" was already used` — неловимое из композиции
падение процесса. Возникало, когда API возвращал повторяющиеся сущности
(каталог VK регулярно отдаёт один и тот же артист/плейлист в разных блоках
и в `links[]`).

| # | Место | Причина | Статус |
|---|-------|---------|--------|
| CRASH-1 | `MusicScreen` → секция «Артисты» (`key = "artist_${it.id}"`) | Артисты из `links[]` приходят с **hardcoded `id = 0L`** у всех → при ≥2 артистах все ключи `"artist_0"` | ✅ Fix #281: `finalizeAudioSearchResult` (дедуп: артисты id>0 → по id, иначе по имени) + itemsIndexed-ключи с индексом в MusicScreen (crash-proof) |
| CRASH-2 | `MusicArtistsScreen` → `items(key = { it.domain ?: it.id.toString() })` | При ≥2 артистах без `domain` (slug не извлёкся) все ключи `"0"` → краш. `audioSearchArtists` дедуп НЕ делает (он — только у потребителя `finalizeAudioSearchResult`, которого этот экран не использует) | ✅ **Настоящий коммит** (единственный оставшийся краш-вектор): `itemsIndexed`-ключ `"artist_${i}_${domain ?: name}"` |
| CRASH-3 | `MusicScreen` → секция «Плейлисты» (`pl_${ownerId}_${id}`) | `audioSearchPlaylists` без дедупа → дубликаты `(ownerId, id)` | ✅ Fix #281: дедуп в `finalizeAudioSearchResult` + index-ключи |
| CRASH-4 | рендер результатов `MusicScreen` | страховка на месте рендера | ✅ Fix #281: itemsIndexed-ключи `artist/pl/track_${idx}_…` |
| CRASH-5 | `MusicAlbumsScreen` → `items(key = "${ownerId}_${id}")` | `audioSearchAlbums` дедупирует внутри (seen-set) — риск низкий, но индекс-ключ гарантирует uncrashable | ✅ **Настоящий коммит**: `itemsIndexed`-ключ `"album_${i}_${ownerId}_${id}"` |

### 1.2 ANR-векторы («приложение не отвечает»)

| # | Место | Причина | Статус |
|---|-------|---------|--------|
| ANR-1 | **`AppLog.appendToFile`** — ГЛАВНЫЙ КОРЕНЬ | write+flush+file.length() **на потоке вызывающего (включая MAIN)** под `persistLock`. Всплеск логов при поиске (AppLog.api на каждый запрос + W-логи fallback) + фоновый спам поллеров → MAIN занимался дисковым I/O и ждал лок → jank/ANR | ✅ Fix #281: однопоточный daemon-executor «PinoK-LogWriter» — вызывающий поток только ставит задачу; форматирование/запись/batch-flush/rotation — на writer-потоке |
| ANR-2 | fallback `audioSearchWithSections` | до 3 повторных HTTP-вызовов того же `catalog.getAudioSearch` (внутри audioSearch→fallback, audioSearchArtists, audioSearchPlaylists) — каждый re-download + re-parse 200–500KB под rate-limit 3 rps | ✅ Fix #281: ОДИН catalog-вызов, артисты/плейлисты добираются из того же ответа (`links[]`/`albums[]`/`playlists[]`), `allowCatalogFallback=false` |
| ANR-3 | `MusicScreen` поисковый эффект | `LaunchedEffect(searchQuery)` — перезапуск на КАЖДОЕ нажатие; collect ловил CancellationException в catch(Exception) и затирал результат пустым → вспышка «Ничего не найдено» + зомби-работа | ✅ Fix #281: `LaunchedEffect(Unit)` + `collectLatest` (отмена in-flight с OkHttp-cancel) + явный rethrow CancellationException |
| ANR-4 | `audioSearchWithSections` (API-уровень) | 4 catch-блока (`catalogRaw`, `audio.search`, `audio.searchArtists`, `audio.searchPlaylists`) глотали `CancellationException` → после cancel корутина продолжала зомби-fallback-запросы | ✅ **Настоящий коммит**: rethrow во всех 4 catch — structured concurrency восстановлена для всех потребителей |

### 1.3 Исключено как причина (проверено)

- `rateLimitWait()` — delay-based, не блокирует поток.
- `callInternal` — OkHttp `enqueue` + `suspendCancellableCoroutine` (OkHttp-cancel
  при отмене), `JsonParser.parseString` — в OkHttp-потоке.
- Парсеры каталога — обёрнуты try/catch; AsyncImage-карточки — Coil вне MAIN.
- Тяжёлый JSON→модели парсинг: все актуальные пути поиска идут под
  `withContext(Dispatchers.IO)` из MusicScreen — отдельный перенос на Default не требуется.

### Чеклист проверки за пользователем (сборка HEAD ≥ настоящего коммита)

1. **Поиск на вкладке «Моя музыка»**: быстрые подряд-запросы («к», «короткие»,
   «короткометражки») — приложение не закрывается, ANR нет; результаты
   заменяют друг друга без «Ничего не найдено»-вспышек.
2. **Повторные поиски** — «Артисты»/«Плейлисты»/«Треки» рендерятся; тап по
   треку играет список результатов.
3. **Библиотека → Артисты и кураторы**: поиск (часть артистов без slug) —
   список рендерится, краша нет, тап открывает артиста.
4. **Библиотека → Альбомы**: поиск — список рендерится, дубликаты отсутствуют.
5. Поиск БЕЗ сети → «Ничего не найдено», без краша (offline-guard не менялся).
6. Если воспроизведётся — `adb logcat -d -b crash` (искать
   `IllegalArgumentException: Key .* was already used` / `Input dispatching
   timed out`) и прислать.
