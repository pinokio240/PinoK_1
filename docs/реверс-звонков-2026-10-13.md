Ключевые наблюдения:
- Параметры `platform/appVersion/version/device/capabilities/clientType/tgt` клиент до-добавляет к `endpoint`, который сервер отдал в ответе `vchat.startConversation`. Тот endpoint содержал **только** `userId&entityType&conversationId&token` (см. §2).
- `deviceIdx=0` появляется в URL **только у входящего** (хотя сервер в ответе startConversation для исходящего тоже отдал `device_idx:0`). Значит построение URL для входящего/исходящего — отдельные ветки кода.
- `clientType` разный по регистру — вероятно, в исходящем берётся из ответа сервера (`client_type:"VK"`), а во входящем — из LP/события входящего звонка (`vk`).

### 1.4. От чего зависит отсутствие `obsolete_client.contact_call`
Из сопоставления HAR (реальный рабочий web-клиент) и кода `p-6 vendors`:
- `version=5` (сигнaling protocol version; в старом PinoK было 1).
- `clientType=VK` (upper, из ответа сервера; в PinoK ошибочно слали `USER`).
- `capabilities=6D7F` (hex-битмаска возможностей клиента; в PinoK было 0).
- `tgt`: `start` для исходящего, `accept` для входящего. При подключении до/в момент старта — `start`.
- `token` — одноразовый bearer, выдаётся `vchat.startConversation` (исходящий) либо по WS/событию для входящего.
- Для входящего также `deviceIdx=0` и `clientType=vk`.

Это подтверждает и даже уточняет предыдущий фикс PinoK (VASI-CALLS-PROTOCOL): version=5 ✓, capabilities=6D7F ✓, clientType=VK ✓ (для исходящего; для входящего — lowercase `vk`), tgt=start ✓ (исходящий), **добавлено:** для входящего tgt=accept + deviceIdx=0.

### 2.2. Источник `session_key` — `auth.anonymLogin` (из `p-6 vendors`)

```js

            client_version: x.split("-")[0], client_type: "SDK_JS" } };
return this.authToken && (t.session_data.auth_token = this.authToken, t.session_data.version = 3),
```

- Серийная авторизация: `session_data.version=2` (без токена) или `version=3` + `auth_token`.

## 3. Медиа / SDP / кодеки / ICE

### 3.1. Кодеки (из `codec_usage` в clientStats)
- Аудио (в обоих дампах): `codec_implementation="audio/opus/encoder"`, `string_value="dred=100;minptime=10;usedtx=1;useinbandfec=1"`.
  - `dred=100` — Duplicated REDundancy: дублирование данных для устойчивости к потерям (мс запас).
  - `minptime=10` — минимальный пакетный интервал 10 мс.
  - `usedtx=1` — Discontinuous Transmission (тишина не шифруется пакетами, экономия трафика).
  - `useinbandfec=1` — встроенная FEC (In-band Forward Error Correction) для борьбы с потерями.
  → В SDP offer/answer/web-клиента ожидается именно такой fmtp для `audio/opus` (rtpmap Opus/48000/2). Необходимо, чтобы совпадал в answer.
- Видео (исходящий дамп): `codec_implementation="video/H265/encoder/MediaFoundationVideoEncodeAccelerator (AMDh265Encoder)"`, `value=12442` (примерные накопленные биты). ⟹ web-клиент использует **H.265 (HEVC)** кодирование на железном ускорителе.
- Звук обрабатывается wasm `calls-sdk` → `audio-processing/0-0-9/wasm_bindings.wasm` + `.data` (загружаются в начале звонка).
- sdk: `sdk_type="WEB"`, `sdk_version="2.8.13-beta.6"`, `app_version="0.0.0"`, `platform="vk_mvk"`, `version:1` (метрик), `call_topology:"D"` (Direct, 1-на-1).

### 3.2. ICE-кандидаты / transport (из clientStats `api_call`,`web-socket`,`sdp_received/generated`)
Входящий (аудио, поднялся шустро, srflx):

## 6. Что подтвердилось / что нет (против предыдущей гипотезы PinoK)

Предыдущая гипотеза (worklog VASI-CALLS-PROTOCOL, из старого HAR): «сервер ждёт version=5, clientType=VK, capabilities=6D7F, tgt=start; PinoK слал 1/USER/0 → obsolete_client». В PinoK уже внесён фикс: PROTOCOL_VERSION 1→5, CLIENT_TYPE=VK, CAPABILITIES 0→6D7F, tgt=start.

**Подтвердилось (по данным 2026-10-13):**
- ✅ `version=5` в WS URL и `protocolVersion=5` в startConversation.
- ✅ `capabilities=6D7F` в обоих дампах.
- ✅ `clientType=VK` для исходящего (совпадает с `client_type:"VK"` из ответа startConversation).
- ✅ `tgt=start` для исходящего.
- ✅ Правка для HTTP: `vchat.startConversation` параметры верные (`externalIds` = чистый uid, `payload.caller_app_id`, `isVideo`, `protocolVersion`), `vchat.hangupConversation` = `conversationId+reason=HUNGUP+peerId`.
- ✅ `clientStats` формат: `data` = JSON с `app_version/sdk_type/sdk_version/version/items[]/platform`, `items[].name` вроде `call_init/call_start/call_accepted_*/call_finish/codec_usage/signaling_command_summary/...`.

**НЕ подтвердилось / уточнилось:**
- ❌ **HTTP-акцепт входящего отсутствует.** Нет `vchat.acceptConversation` по HTTP; приём — WS `accept-call` (после `get-rooms`). Если PinoK планировал HTTP-акцепт — это неверно, принятие только через WS.
- ⚠️ **Входящий WS URL использует `clientType=vk` (нижний регистр) и добавляет `deviceIdx=0`, `tgt=accept`** — отличается от исходящего (`clientType=VK`, нет deviceIdx, tgt=start). Для входящего PinoK должен слать tgt=accept (+deviceIdx), а не tgt=start.
- ⚠️ **TURN/STUN credentials приходят от сервера** (в `startConversation` для исходящего; по WS для входящего) — не нужно хардкодить.
- ⚠️ **peerId для hangup** — спец-формат `3897xxxxxxxxx`, не равен user id. Для исходящего конкретное значение `38970049966` зависит от звонка.

**Точные JSON-схемы WS-команд (accept-call/get-rooms/transmit-data/…) из бандлов восстановить НЕ удалось** — код calls-sdk (`calls-sdk.cdn-vk.ru`) отсутствует в дампах (в HAR видны только `.wasm`/`.data`). Из бандлов видно только:
- HTTP-транспорт fb.do + auth.anonymLogin (цитаты в §2).
- Строки `sdp`, `inviteType:"ANSWER"/"OFFER"/"CANDIDATE"`, `streamKey`, `callSupport`, `handleJoinMessage/handleStatusMessage` — это код RTC-стриминга видеоплеера (H264), НЕ код звонков.
- `request_id` — используется в ws-обёртке для запрос-ответов (общий паттерн calls/streaming), но не в звонковом контексте данного дампа.

Если нужны **точные тела WS-команд**, правильный следующий шаг — перехват `/ws2` через прокси (mitmproxy/Burp) во время реального звонка, либо загрузка `calls-sdk` JS с CDN и деобфускация.
