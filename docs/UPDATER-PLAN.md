# PinoK — план развития обновления приложения через git

> Статус: ПЛАН (код не писался — по запросу пользователя 2026-09-13).
> Базис: существующий in-app updater (Fix #391 #IN-APP-UPDATER, волна 29-i) —
> `app/src/main/java/re/pinok/updater/UpdaterManager.kt`, UI `SettingsScreen.kt` →
> вкладка «Обновления» (`UpdateTab`), манифест `version.json` в корне ветки,
> инструкция `docs/UPDATER.md`. Этот план — расширение и укрепление, не переписывание.

---

## 0. Резюме

Обновление уже работает по схеме «манифест в git + APK в GitHub Releases»: приложение
читает `version.json` через raw.githubusercontent.com, сравнивает `versionCode`,
качает APK, сверяет SHA-256, запускает системный установщик. Бэкенда нет и не нужен —
публикация релиза = обычный `git push`.

Чего не хватает (зафиксировано в `docs/UPDATER.md` §4 и ревизии кода):

| № | Пробел | Влияние |
|---|--------|---------|
| 1 | Нет автопроверки (ни при запуске, ни по расписанию) — только кнопка | Юзер не узнаёт о релизе |
| 2 | `MANIFEST_URL` — жёсткая константа в коде | Сменить источник можно только пересборкой |
| 3 | Нет уведомлений и баннера «доступна новая версия» | Обновление не анонсируется |
| 4 | Загрузка без foreground-сервиса, без Range-resume | Свёрнул приложение — качание могло оборваться |
| 5 | В `version.json` пока ни одной опубликованной сборки (`apkUrl: ""`) | Обновляться пока физически не с чем — первый релиз не состоялся |
| 6 | Release-сборка unsigned, подписание вручную apksigner | Риск забыть/потерять keystore |
| 7 | Нет самоочистки `updates/` и post-update-хука | Мусор от APK, нет «обновлено до X» |

План разбит на 3 волны: **A** — ядро (сменный источник + автопроверка при запуске +
баннер), **B** — фон и удобство (WorkManager, уведомления, очистка, self-check подписи
APK), **C** — опционально (Releases API, Wi-Fi-only, CI-автоматизация, каналы).

## 1. Модель «обновления через git» — как это устроено и почему так

**Схема (остаётся основной):**

```
разработчик                      GitHub                        устройство
─────────────                    ─────                         ──────────
bump versionCode ─┐
сборка+подпись   ─┤→ git push → raw.githubusercontent.com ←── GET version.json (ETag)
APK → Release    ─┤   ветки PinoK      (CDN-кэш ~5 мин)         ↓ Gson-парс
sha256 → version.json ─┘                                        ↓
                                                        max(versionCode) ?
                                                        > установленного
                                                                ↓
                                              баннер/уведомление → UpdateTab
                                                                ↓
                                     OkHttp-стрим → updates/*.apk → SHA-256
                                                                ↓
                                     FileProvider-URI → системный установщик
```

**Почему манифест-в-ветке, а не GitHub Releases API:**

- raw.githubusercontent.com — без rate-limit'ов на практике, без токена для публичного
  репо, отдаёт статичный JSON; api.github.com неавторизованно — жёсткие 60 запросов/час
  на IP (при периодических автопроверках на многих устройствах за NAT — риск 403).
- Манифест живёт в ветке и попадает в историю git — «кто когда что опубликовал» видно
  в диффах; APK при этом кладётся в Releases-ассеты (не git-объекты, лимит git 100 МБ
  на файл не мешает).
- Схема тривиально расширяема: тот же `apkUrl` может указывать на любой https-хост.
- Releases API остаётся **резервным источником** (волна C): `GET
  /repos/{owner}/{repo}/releases/latest` → тег + ассеты; нужен только если захотим
  авто-обнаружение релизов без правки манифеста.

**Ключевой инвариант: «новее» определяется только `versionCode`** (Int, монотонный),
как для Android PackageInstaller, так и для updater'а. `versionName`/`stamp`/`notes` —
отображение.

## 2. Как приложение «следит» за релизами (мониторинг)

Пуш-канала нет (нет FCM/бэкенда) — слежение возможно только опросом (polling).
Набор стратегий, включаемых пользователем (сохраняем философию проекта «ноль
фонового трафика без ведома юзера» — `docs/UPDATER.md` прямо фиксирует, что
автопроверка при запуске отсутствовала *сознательно*):

| Код | Стратегия | Триггер | По умолчанию |
|-----|-----------|---------|--------------|
| M1 | Ручная проверка | кнопка «Проверить обновления» в UpdateTab (есть) | — |
| M2 | При открытии вкладки «Обновления» | авто-GET при первом входе в таб за сессию | ВКЛ (дёшево, юзер сам пришёл) |
| M3 | Проверка при запуске приложения | через 10–15 с после старта, один раз за процесс | ВЫКЛ (тумблер в UpdateTab) |
| M4 | Периодическая фоновая | WorkManager periodic 24 ч, constraint NetworkType.CONNECTED (прецедент — `CookieRefreshWorker`, 6 ч) | ВЫКЛ, включается вместе с M3 или отдельно |
| M5 | Баннер/уведомление по результату | любой успешный Available | ВКЛ |

**Троттлинг и честность:**

- `update_last_check_ms` в SovaPrefs: автопроверка (M3/M4) не чаще интервала, даже
  если приложение перезапускалось; M1/M2 — без троттлинга (явное действие юзера).
- Бэкофф при сбоях: 1 ч → 6 ч → 24 ч (кап), сброс на успехе. Офлайн — не «нет
  обновлений», а честное «проверка не выполнена: нет сети» (принцип honest states).
- Условные запросы: хранить `ETag` из ответа raw.githubusercontent.com, слать
  `If-None-Match`; 304 Not Modified = ноль трафика и ноль парсинга.
- Никаких push-уведомлений «о релизе» извне: GitHub может слать Watch-письма юзеру —
  это его личный канал, к приложению отношения не имеет (зафиксировать в UPDATER.md).

## 3. Как определяется «есть новая версия» (алгоритм)

1. GET `<manifest_url>` (10 с таймауты — свой лёгкий OkHttpClient в UpdaterManager,
   без VK-cookie-jar; клерtext глобально запрещён — только https).
2. Парс Gson → `UpdateManifest(versions: List<UpdateInfo>)`.
   Битый JSON/пустой массив → `ParseError` с честным текстом, состояние не ломать.
3. Выбор кандидата: **максимальный `versionCode` по всему массиву** (порядок записей
   не полагается ни на что — сегодня «новые первыми» по доке, правило кода от порядка
   не зависит).
4. Сравнение с `BuildConfig.VERSION_CODE`:
   - `max > установленного` → `Available`; если у записи пустой `apkUrl` → честный
     стейт «доступна X, но APK не опубликован», кнопки задизейблены (уже так);
   - `max == установленного` → `UpToDate`; если при этом `stamp` из манифеста ≠
     `BuildStamp.STAMP` → нейтральная строка «версия та же, штамп сборки отличается»
     (помогает при пересборках того же versionCode);
   - `max < установленного` (кастомный источник/форк со старым манифестом) →
     информативное «на источнике нет сборок новее установленной», не ошибка.
5. Отдельные списки: записи с versionCode **больше** — «доступные», **меньше** —
   «откат» (кнопка с AlertDialog о потере данных — уже есть; ограничение ОС
   `INSTALL_FAILED_VERSION_DOWNGRADE` обходится только удалением приложения —
   честно задокументировано в UPDATER.md §2, программно не обходится).

**Эволюция схемы манифеста:** только аддитивно (новые поля Gson молча игнорирует
старыми клиентами). Переименование/удаление полей запрещено; при необходимом
ломающем изменении — поле `"schema": 2` и старым клиентам честная «источник новой
схемы не поддерживается этой сборкой». **Кэш CDN ~5 мин**: сразу после push проверка
может вернуть старый манифест — это норма; кнопке «Проверить снова» можно добавить
cache-buster-параметр `?t=<мс>` (raw такое отдаёт заново).

## 4. Смена гит-ссылки (кастомный источник обновлений)

**Хранение — SovaPrefs (DataStore `sova_settings`), новые ключи:**

| Ключ | Тип | Дефолт | Назначение |
|------|-----|--------|------------|
| `update_manifest_url` | String | встроенная константа | источник манифеста |
| `update_token` | String | `""` | Bearer-токен для приватного репо (маскировать в UI) |
| `update_autostart_check` | Boolean | `false` | M3 |
| `update_periodic_check` | Boolean | `false` | M4 |
| `update_last_check_ms` | Long | 0 | троттлинг/бэкофф |
| `update_etag` | String | `""` | условный запрос |
| `update_skipped_code` | Int | 0 | «пропустить эту версию» |
| `update_last_manifest_json` | String | `""` | кэш для оффлайн-просмотра вкладки |

**UI — новая секция «Источник обновлений» в `UpdateTab` (SettingsScreen.kt, ~4549):**

- поле URL + кнопка «Сбросить на стандартный» (`pinokio240/PinoK_1`, ветка PinoK);
- кнопка «Проверить ссылку»: GET + парс + честный вердикт (недоступен / не JSON /
  нет версий / ok: N версий, новейшая X) — до сохранения;
- опциональное поле токена (парольный TextField, показывается маскированно; шлётся
  ТОЛЬКО по https как `Authorization: Bearer`; предупреждение, что токен лежит
  локально в настройках приложения);
- при активном не-дефолтном источнике — постоянный жёлтый баннер вверху вкладки:
  «Источник обновлений изменён: <host>. Сборки с этого источника не контролируются
  автором приложения».

**Сценарий применения:** тестер/форковщик переключает URL на свой форк и получает
пререлизы, не трогая основную аудиторию. Смена источника сбрасывает `update_etag`
и `update_last_check_ms`; ключ оффлайн-кэша включает URL, чтобы источники не
перемешивались.

**Безопасность при кастомном URL (важно):**

- https уже гарантирован глобально (`usesCleartextTraffic=false`), но владелец
  кастомного манифеста контролирует и `apkUrl`, и `sha256` — то есть sha256 при
  злом источнике не защита. Единственная настоящая защита — **проверка подписи
  скачиваемого APK** (см. §6, волна B, п. 9): дайджест сертификата APK сверяется
  с сертификатом самого работающего приложения; чужая сборка отвергается до
  передачи установщику.
- **РЕАЛИЗОВАНО волной 46 (#UPDATER-SIGNING):** манифест версий теперь
  ed25519-подписывается ключом релиз-менеджера (detached version.json.sig,
  публичный ключ в APK), проверка — ДО парсинга/установки, fail-closed.
  Злой источник больше не может подставить свой apkUrl/sha256 даже при полном
  контроле над своим манифестом: подписи релиз-менеджера у него нет. Проверка
  сертификата APK (волна B, п. 9) остаётся следующим рубежом.
- Токен приватного репо: право read-only (classic `public_repo`/fine-grained
  Contents:Read), никогда не коммитится (чек-лист check-secrets это ловит).

## 5. Какие действия требуются (волны внедрения)

### Волна A — ядро (ориентир: 6–8 файлов)

1. **SovaPrefs**: ключи из §4 + дефолты в companion (паттерн существующих ~100 ключей).
2. **UpdaterManager**: чтение URL/токена из prefs (изменяемо в рантайме), ETag-логика,
   троттлинг/бэкофф, `checkNow(force: Boolean)`, честные стейты «источник старее
   установленного» и «версия та же, штамп другой»; ретро-совместимость схемы.
3. **UpdateTab**: секция «Источник обновлений» (§4), тумблер «Проверять при запуске»,
   «Пропустить эту версию» (кнопка у карточки Available; skipped_code учитывается в
   баннере M5, но не в UpdateTab).
4. **Баннер Available** поверх главного экрана — паттерн `OfflineBanner.kt`:
   «Доступна версия 2.1.0 — Что нового… — Обновить / Позже / Пропустить»; тап →
   UpdateTab; не показывать, если versionCode == skipped_code.

### Волна B — фон, уведомления, надёжность (ориентир: 6–9 файлов)

5. **UpdateCheckWorker** (WorkManager, прецедент `CookieRefreshWorker`): periodic
   24 ч, `NetworkType.CONNECTED`, результат в prefs (`update_last_result_json`),
   уведомление только при Available и только если юзер включил автопроверку.
6. **Канал уведомлений «Обновления»** — идемпотентное создание по прецеденту
   сервисов (`MessageNotifier`/`*DownloadService`), низкая важность, тап →
   MainActivity-интент с флагом «открыть UpdateTab» (екстры навигации уже умеет
   SovaNavHost — сверить при реализации).
7. **Self-check подписи APK** (п. §4-безопасность): после sha256 — сравнить дайджест
   сертификата файла с текущим приложением (`PackageManager` по обоим), несовпадение
   → удалить файл, честная ошибка «сборка подписана другим ключом».
8. **Очистка**: держать в `updates/` ≤ 2 APK (текущий + предыдущий), удалять
   `.tmp`-хвосты при старте приложения, удалять APK после успешного входа в
   обновлённую версию.
9. **Post-update хук**: `BootReceiver` уже слушает `MY_PACKAGE_REPLACED` — добавить
   ветку: сравнить сохранённый `update_installed_code` с новым versionCode →
   тихий тост/уведомление «Обновлено до 2.1.0», чистка кэшей обновлений.
10. **Foreground-скачивание** (опционально в этой волне): паттерн
    `VideoDownloadService` — уведомление с прогрессом; снимает риск убитого
    процесса при сворачивании (UPDATER.md §4, п. 1). Альтернатива дешевле —
    Range-resume для `.tmp` (Range-запрос, дописать файл) — выбрать при реализации.

### Волна C — опционально / будущее

11. Резервный источник GitHub Releases API (§1) с троттлингом ≥ 1 ч и честным
    «лимит GitHub API исчерпан».
12. Тумблер «Только Wi-Fi» для скачивания APK.
13. CI-автоматизация релиза (GitHub Actions: тег → assembleRelease → подпись из
    Secrets → Release-ассет → авто-правка version.json → push). Риск: keystore в
    секретах репо — заводить только если случится утечка-парано́я, иначе ручной
    путь из UPDATER.md остаётся надёжнее.
14. Каналы обновлений (стабильная/бета) — префиксные записи в манифесте + селектор.
15. ABI-сплиты (arm64/arm/universal) — только если реально понадобится: пары
    apkUrl-полей + `Build.SUPPORTED_ABIS`.
16. ✅ «Откат на конкретную версию» — РЕАЛИЗОВАНО волной 45 (#UPDATER-ROLLBACK):
    список «Версии из манифеста» переживает перезапуск процесса (кэш сырого JSON
    манифеста в SovaPrefs `update_last_manifest_json` + восстановление в
    `ensureInit`); «Откатиться» качает APK в ПУБЛИЧНЫЕ Загрузки
    (системный DownloadManager, `Загрузки/PinoK/…`) — файл переживает удаление
    приложения, в отличие от app-specific `updates/`; диалог расписывает порядок:
    экспорт настроек → скачивание → удаление → установка из Загрузок. Смена
    источника сбрасывает кэш манифеста (`onSourceChanged`).
17. ✅ Экспорт/импорт настроек — РЕАЛИЗОВАНО волной 45 (#SETTINGS-EXPORT): вкладка
    «Данные» (Настройки → Данные): полный дамп ВСЕХ ключей DataStore
    (`SovaPrefs.rawSnapshot()` — generic по типам string/boolean/int/long/
    stringSet, новые ключи подхватываются без правок) → JSON `format=1` через
    SAF CreateDocument; импорт через OpenDocument → parse → подтверждение →
    атомарное применение (`restoreRaw()` — одна транзакция). В файле лежат
    куки/токены сессии — предупреждение в UI до экспорта.

### Что сознательно НЕ входит (out of scope)

- Дельта-обновления (diff-патчи) — APK 50–100 МБ, экономия не окупает сложность.
- Push через FCM — нет бэкенда.
- «Бесшовный» откат ОДНОЙ кнопкой (авто-удаление + авто-установка + авто-
  восстановление) — по-прежнему нет: Android не даёт ставить старую версию
  поверх и не позволяет приложению удалить себя незаметно. Полуавтоматический
  путь реализован волной 45 (пп. 16–17: откат через публичные Загрузки +
  экспорт/импорт настроек; удаление и установка — руками юзера, порядок
  подсказан в диалоге).
- Автоустановка без явного согласия юзера — никогда (принцип).

## 6. Чек-лист релиза (действия при каждом обновлении) — расширение UPDATER.md §1

1. `versionCode` строго **+1** относительно максимума **опубликованных** записей
   (не только установленной!) — правило монотонности protects от даунгрейд-ловушек.
2. `versionName` + `BuildStamp.STAMP` (штамп обязателен — он же в манифесте).
3. Сборка → **подпись тем же keystore** → APK.
4. APK → GitHub Release на тег `v<versionName>` → взять постоянную ссылку ассета.
5. `sha256sum` → новая запись **первой** в `version.json` (`apkUrl`, `sha256`,
   `notes` на русском, старые записи не удалять — нужен откат).
6. `git push origin PinoK` → подождать ≤ 5 мин CDN-кэша → проверить: curl raw-URL
   с устройства/браузера, затем «Проверить обновления» в приложении.
7. Раз в N релизов: убедиться, что keystore и пароли лежат в ≥ 2 местах (потеря
   ключа = юзерам понадобится удаление приложения с потерей сессий — см. §2 UPDATER.md).

## 7. Прочие нюансы и риски (сводный список)

| Область | Нюанс | Как закрываем |
|---------|-------|----------------|
| Подпись | Другой keystore → `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | Один keystore навсегда; self-check (B-7) ловит и чужие файлы |
| Даунгрейд | ОС не ставит старее поверх новее | Кнопка отката честно ведёт через удаление (уже есть); правило монотонного versionCode |
| Play Protect | Может пометить сторонний APK | Текст в UpdateTab: «Если установщик предупреждает — это сторонняя установка, подпись проверена sha256+ключом» |
| Unknown sources | Per-app разрешение на Android 8+ | Уже обработано (`canRequestPackageInstalls` → `ACTION_MANAGE_UNKNOWN_APP_SOURCES`) |
| Место | Закончилось место под APK | `StatFs` перед загрузкой → честная ошибка «нет места (нужно X МБ)» |
| Doze/батарея | WorkManager сам уважает Doze; `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` в манифесте НЕ использовать для обновлений | Только констрейнты Worker'а |
| Сеть | Клерtext запрещён глобально; `net_ssl_pinning`/прокси — настройки сети приложения, сырые raw.githubusercontent не пинятся | Свой OkHttpClient updater'а без cookie-jar; при прокси-настройке — задокументировать, что обновления идут мимо прокси (или переиспользовать общий клиент — решить в волне A) |
| Rate-limit | raw — CDN без практичных лимитов; api.github.com — 60/ч неавторизованно | Releases API только как резерв с троттлингом |
| Кэш CDN | 5 мин после push виден старый манифест | Документировать; cache-buster для ручной кнопки |
| Конфиденциальность | Автопроверка = GET на github без данных юзера | Зафиксировать в UPDATER.md; автопроверка ВЫКЛ по умолчанию |
| Часы устройства | Не строить интервалы на доверии к времени | Считать по `System.currentTimeMillis` только для троттлинга (безопасно), не для «сегодня/вчера» |
| Локализация | Все новые строки — русский, honest texts | Конвенция проекта |
| Код-стайл | `#NULL-EXPLICIT` (ноль `!!`), честные ошибки, большие русские KDoc, штамп сборки | `CODING_STYLE.md` |
| Совместимость | Старые клиенты должны пережить новые поля манифеста | Только аддитивные изменения схемы |

## 8. Тест-план (после волн A/B)

Хеппи-путь: форк-URL с тестовым манифестом → баннер → скачивание → установка.
Негативы: 404 (приватный/битый URL), не-JSON, пустой versions, sha-мисматч,
APK чужой подписи (B-7), офлайн, мало места, убийство процесса посреди загрузки,
`versionCode` источника меньше установленного, «пропустить версию» гасит баннер,
ETag/304 не переедает трафик, уведомление открывает UpdateTab, очистка updates/,
`MY_PACKAGE_REPLACED` показывает «Обновлено до X». Устройства: API 24 (minSdk),
26 (install-permission ветка), 34+ (foreground-политики).
