# PinoK — обновление и откат приложения через git (Fix #391 #IN-APP-UPDATER)

In-app updater читает **version.json** из корня ветки `PinoK` репозитория
`pinokio240/PinoK_1` через `raw.githubusercontent.com`, показывает список версий,
качает APK, проверяет SHA-256 и запускает системный установщик. Никакого бэкенда —
публикация релиза = обычный `git push`.

Код: `app/src/main/java/re/pinok/updater/UpdaterManager.kt`,
UI: `SettingsScreen.kt` → вкладка «Обновления» (`UpdateTab`).

---

## 1. Публикация новой версии (чек-лист релиза)

1. **Bump версии** в `app/build.gradle.kts`:
   ```kotlin
   versionCode = 2        // строго +1 (или больше) относительно предыдущей
   versionName = "2.1.0"  // свободная строка
   ```
   `versionCode` — единственный критерий «новее/старше» для Android и для
   updater'а (сравнивается с `BuildConfig.VERSION_CODE`).

   **Нюанс тестовых debug-сборок (#RELEASE-V211-TEST):** debug-сборка, собранная
   без bump'а, несёт в APK СТАРЫЙ versionCode (APK нельзя изменить постфактум).
   Updater предлагает обновление только когда `versionCode` из манифеста **строго
   больше** установленного: публиковать надо код, БОЛЬШИЙ кода установленных
   сборок (переустановка с тем же versionCode разрешена, даунгрейд — нет).
   Пока установлена сборка со старым кодом, предложение обновления не исчезает —
   оно гасится кнопкой «Пропустить эту версию» до выхода сборки, чей
   собственный versionCode сойдётся с манифестом.

2. **Локальная сборка signed release APK на Windows:**
   ```
   gradlew assembleRelease
   ```
   Release-сборка сейчас unsigned (`signingConfig` не задан в build.gradle.kts) —
   подпишите вручную:
   ```
   apksigner sign --ks <keystore.jks> --out PinoK_2.1.0_2.apk app-release-unsigned.apk
   ```
   Или используйте Android Studio → Generate Signed Bundle/APK.
   **ВАЖНО: одна и та же пара ключей (keystore) для всех релизов** — Android
   откажется ставить APK поверх установленного приложения, если подпись другая
   (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`).

3. **Публикация APK** — где взять `apkUrl` (любое постоянное хранилище):
   - **GitHub Releases** (рекомендуется): создайте Release на тег версии,
     приложите APK, возьмите постоянную ссылку ассета, например
     `https://github.com/pinokio240/PinoK_1/releases/download/V2.1.4/Pinok_1509000.apk`
     (живой пример релиза 14.09: имя ассета произвольное — берётся точная
     ссылка со страницы Release). Ассеты Releases — не git-объекты, теги
     не «съедают» файл при перезаписи ветки.
   - Альтернативы: raw-файл в ветке (для APK >100 МБ упрётесь в лимит git),
     любой статический хостинг/CDN с постоянным URL.

4. **SHA-256:**
   ```powershell
   Get-FileHash PinoK_2.1.0_2.apk -Algorithm SHA256
   ```
   ```bash
   sha256sum PinoK_2.1.0_2.apk
   ```

5. **Записать в `version.json`** (в корне репо, ветка PinoK): новая версия —
   **ПЕРВОЙ** в массив `versions`, старые записи НЕ удалять — они нужны для
   отката (исключение — тестовые релизы: по решению релиз-менеджера массив
   может содержать только актуальную запись; прецедент V2.1.1-test 13.09 —
   предыдущая v2.1.0-test затёрта и удалена с GitHub; с V2.1.1-test все релизы
   идут одной записью). Живой пример — запись V2.1.4 после публикации 14.09
   (notes сокращён, полный — в version.json):
   ```json
   {
     "versions": [
       {
         "versionCode": 5,
         "versionName": "2.1.4",
         "stamp": "calls-2026.09.06-5",
         "apkUrl": "https://github.com/pinokio240/PinoK_1/releases/download/V2.1.4/Pinok_1509000.apk",
         "sha256": "c146d461035f179d00642e95f0a9083a6d257c3ddc1f83ffd2a77d7734881532",
         "notes": "Сборка V2.1.4 (debug): каналы (#CHANNELS-HIST), ускорение «Сообщений» (#IM-FAST-LIST), #NET-CANCEL-RETRY — ..."
       }
     ]
   }
   ```
   **Двухфазный релиз (прецедент V2.1.4, 14.09):** запись можно готовить
   ДО сборки и публикации APK — с пустыми `apkUrl=""` и `sha256=""`. Апдейтер
   на такой версии честно отвечает «APK ещё не опубликован» (UpdaterManager,
   кнопки скачивания задизейблены) — тестеры не ломаются. После публикации
   APK заполните оба поля и ОБЯЗАТЕЛЬНО переподпишите манифест (шаг 6):
   подпись накрывает точные байты version.json — правка без ре-подписи
   отклоняется всеми установками (fail-closed).
   Поля:
   - `versionCode` — Int, критерий сравнения (обязателен);
   - `versionName` — показывается в UI;
   - `stamp` — штамп сборки `BuildStamp.STAMP` (проверка «тот ли код в APK»);
   - `apkUrl` — прямая ссылка на APK; **пустая строка = APK не опубликован**,
     кнопки скачивания у этой версии будут задизейблены с пояснением;
   - `sha256` — контрольная сумма (hex, регистр/пробелы не важны). Пустая —
     проверка целостности пропускается (не рекомендуется);
   - `notes` — строка-описание в списке версий.

6. **Переподписать манифест (волна 46 #UPDATER-SIGNING, ОБЯЗАТЕЛЬНО):**
   ```bash
   python3 tools/updater-sign/sign_manifest.py sign version.json
   git add version.json version.json.sig
   ```
   Переподписывается КАЖДАЯ правка version.json — включая пост-релизное
   заполнение apkUrl/sha256 при двухфазном релизе (шаг 5) и правки notes.
   Рядом с version.json появится version.json.sig — base64 detached-подпись
   ed25519 РОВНО над байтами version.json. Публичный ключ зашит в APK
   (`UpdaterSigning.RELEASE_PUBLIC_KEY_B64`), приватный — у релиз-менеджера
   ВНЕ репозитория. **Забудете переподписать — все установки отклонят манифест**
   («Манифест ОТКЛОНЁН: подпись не совпала…»): это fail-closed защита, а не сбой.
   Подробности — §3.

7. **`git push origin PinoK`** — приложение увидит обновление:
   - по кнопке «Проверить обновления» (Настройки → Обновления);
   - автоматически при первом входе во вкладку «Обновления» за сессию (M2,
     волна 43 — тихая, с ETag-условным GET);
   - при запуске приложения — ТОЛЬКО если юзер включил «Проверять при запуске»
     (M3, default ВЫКЛ — ноль фонового трафика без ведома юзера; троттлинг 6ч).
   Найденное обновление показывается баннером поверх главного экрана
   (скрывается кнопкой «Пропустить эту версию»; тап по сообщению просто
   прячет баннер до перезапуска приложения — #UPDATER-BANNER-DISMISS,
   это НЕ «пропуск») и карточкой во вкладке.
   raw.githubusercontent кэширует на ~5 минут — сразу после пуша проверка
   может ещё увидеть старый манифест.

## 2. Откат на предыдущую версию (даунгрейд)

Кнопка «Откатиться» показывается у версий с `versionCode` **меньше** текущего.
Механика та же: скачать → установить. Но есть жёсткое ограничение ОС:

- **Android не устанавливает более старую версию поверх новой**
  (`INSTALL_FAILED_VERSION_DOWNGRADE`). Исключение — `adb install -d`
  (debug-only, обычному юзеру недоступно) и системные флаги, которые
  приложению не подвластны.
- Следовательно, реальный путь отката: **удалить приложение → установить
  старый APK**. При удалении теряются ВСЕ данные: сессия (нужно заново
  проходить вход в VK), кэши, офлайн-треки, настройки. Updater честно
  предупреждает об этом в AlertDialog перед откатом — обойти ограничение
  программно нельзя, это защита PackageInstaller'а.

**Волна 45 (#UPDATER-ROLLBACK + #SETTINGS-EXPORT): полуавтоматический откат.**

- «Откатиться» теперь скачивает APK в **публичные Загрузки**
  (`Загрузки/PinoK/PinoK_<имя>_<code>.apk`, системный DownloadManager) —
  файл ПЕРЕЖИВАЕТ удаление приложения (прежде APK уходил в app-specific
  `updates/` и стирался вместе с ним в самый нужный момент).
- Перед удалением настройки переносятся через вкладку **Настройки → Данные →
  «Экспортировать в файл»** (§5), после установки старого APK —
  «Восстановить из файла»: настройки, локальные закладки треков и сессия
  (вход в аккаунт) возвращаются из экспорта.
- Диалог отката расписывает порядок прямо в приложении (экспорт → скачивание
  → удаление → установка из Загрузок).
- Осталось ручным: само удаление приложения и открытие APK из Загрузок —
  программно обойти запрет даунгрейда нельзя (защита PackageInstaller'а).
- Волна 46 (#UPDATER-ROLLBACK-SHA): после скачивания приложение сверяет
  SHA-256 файла с манифестом (через `openDownloadedFile()` — свой download,
  права на хранилище не нужны). Несовпадение → файл УДАЛЯЕТСЯ из Загрузок.
  Если у версии в манифесте не задан sha256 — сверять нечем (диалог отката
  предупреждает об этом заранее). Проверка живёт, пока процесс жив: если
  убить приложение до конца скачивания, пост-проверка не случится.

## 3. Безопасность

- **Подпись манифеста ed25519 (волна 46 #UPDATER-SIGNING, P0 внешнего ревью).**
  До этой волны apkUrl и sha256 лежали в ОДНОМ недоверяемом файле: любой,
  кто контролирует канал (компрометация репозитория, кастомный
  UPDATER-SOURCE, MITM поверх https) мог подменить манифест и заставить
  updater установить произвольный APK. Теперь:
  - приватный ключ ed25519 (32 байта seed, hex) — только у релиз-менеджера,
    ВНЕ git; сгенерирован `tools/updater-sign/sign_manifest.py keygen`;
  - публичный ключ зашит в APK — `app/src/main/java/re/pinok/updater/UpdaterSigning.kt`,
    константа `RELEASE_PUBLIC_KEY_B64` (отпечаток ключа sha256:
    `22520fde561cf545efc7a2d0700b18db1b5cd1b37f520063e603471596489748`);
  - в репозитории рядом с version.json лежит version.json.sig (base64
    detached-подписи над точными байтами манифеста — без канонизации JSON,
    нечему разъезжаться);
  - порядок в приложении: GET version.json (БАЙТЫ) → GET version.json.sig →
    ed25519-верификация (BouncyCastle, легковесный API — java.security
    знает Ed25519 только с API 33, а minSdk = 24) → и только потом Gson-парсинг;
  - **fail-closed**: нет .sig / битый .sig / подпись не совпала / ключ не
    встроен = `SignatureRejected` → манифест не доходит до UI и установки
    (штатный путь И откат получают ноль данных), автопроверка уходит в
    бэкофф, кэш манифеста не перезаписывается (пишется только после
    проверки; 304 Not Modified = тело не менялось — доверие сохраняется);
  - кастомный UPDATER-SOURCE работает только с манифестами, подписанными
    ТЕМ ЖЕ ключом (форк-мейнтейнеру нужна своя пара ключей и своя сборка APK);
  - **ротация ключа** = новая сборка APK с новым `RELEASE_PUBLIC_KEY_B64`;
    старые установки после ротации честно отклоняют манифесты со старым
    ключом — критичное обновление доставляется вручную (сторонняя ссылка);
    **потеря ключа** = вечный fail-closed для существующих установок.
  - Исключение, согласованное с ревьюером: **пустой** version.json
    (blank/`{}`/`null`/`[]`) подписи не требует — устанавливать нечего,
    подделывать нечего; приложение молча показывает «UpToDate — конфиг
    не заполнен» (#UPDATER-EMPTY-CONFIG) вместо ошибки на каждую проверку.
  - Инструмент: `tools/updater-sign/sign_manifest.py` — один файл, ноль
    зависимостей (RFC 8032 reference-математика, selftest по тест-векторам
    RFC 8032 §7.1), команды: keygen / pubkey / sign / verify / selftest.
- **sha256-проверка**: скачанный файл сверяется с `sha256` из манифеста.
  Несовпадение → файл удаляется, состояние `Error`. Защищает от обрыва
  загрузки и от подменённого файла. Доверие к манифесту теперь обеспечено
  его подписью (см. выше): подписаны и apkUrl, и sha256 — вместе, одним
  ключом.
- **Кэш**: APK кладётся в `getExternalFilesDir(null)/updates/` и остаётся
  между сессиями; повторное нажатие «Скачать APK» при совпадающем SHA-256
  не тянет трафик. Битый кэш (обрыв прошлой загрузки) перезакачивается.
- **REQUEST_INSTALL_PACKAGES** (добавлен в AndroidManifest.xml) — normal-level
  permission: позволяет приложению **запрашивать** установку пакетов, рантайм-
  диалога нет. На Android 8+ (API 26+) пользователь дополнительно выдаёт
  per-app разрешение «Установка неизвестных приложений»; `installApk()`
  проверяет `canRequestPackageInstalls()` и при отказе открывает
  `ACTION_MANAGE_UNKNOWN_APP_SOURCES` (без крэша).
- **FileProvider** — уже существующий (`re.pinok.fileprovider`,
  `external-files-path`), установленному пакету выдаётся только read-URI на
  конкретный APK.
- raw.githubusercontent.com — https-only; cleartext в приложении выключен
  (`usesCleartextTraffic="false"`).

## 4. Известные ограничения

- Загрузка без foreground-сервиса: если юзер свернёт приложение на
  середине скачивания, процесс может быть убит ОС — файл останется в
  `.tmp`, повторное «Скачать APK» начнёт заново (Range-resume сознательно
  не используется для APK). Для 50–100 МБ это секунды на Wi-Fi.
- Одна активная загрузка за раз (состояние глобальное) — упрощает UI и
  state-машину; параллельные загрузки APK не нужны.
- Проксирование/зеркала манифеста: с волны 43 (#UPDATER-SOURCE) источник
  ПЕРЕОПРЕДЕЛЯЕТСЯ в настройках (Настройки → Обновления → «Источник обновлений»:
  URL + опциональный Bearer-токен приватного репо + «Проверить ссылку»),
  но активным остаётся ровно ОДИН URL одновременно — зеркала/фолбэки не
  поддерживаются (план волны C — docs/UPDATER-PLAN.md).
- Проверка подписи скачанного APK (сверка сертификата с текущим приложением)
  ещё не реализована — запланирована в волну B. С волны 46 (#UPDATER-SIGNING)
  риск кастомного источника существенно снижен: apkUrl и sha256 доверяются
  только внутри ed25519-подписанного манифеста, неподписанный источник
  отклоняется целиком (fail-closed); жёлтый баннер недоверия во вкладке
  остаётся.
- Фоновая периодическая проверка (WorkManager) — план волны B
  (docs/UPDATER-PLAN.md §5); сейчас только: вручную / при входе во вкладку /
  при запуске по тумблеру.

## 5. Экспорт/импорт настроек (волна 45 #SETTINGS-EXPORT; 45-б — контейнерное покрытие; 45-в — перепроверка восстановления #RESTORE-SAFETY)

- Вкладка **Настройки → Данные** (перед «Обновлениями»): «Экспортировать в
  файл» / «Восстановить из файла».
- Экспортируется ВСЁ хранилище «контейнерного» приложения (волна 45-б —
  приложение не ограничивается одним DataStore):
  - DataStore «sova_settings» (SovaPrefs): настройки всех разделов, локальные
    закладки треков и папок, кэш updater'а;
  - legacy SharedPreferences «equalizer»: настройки эквалайзера медиа-контейнера;
  - сессия входа (EncryptedSharedPreferences через ExchangeTokenStorage):
    access/exchange/webview/silent-токены, remixsid, vk_* куки, trusted_hash,
    re-login креды — прецедент plaintext-файла с токенами уже был (account.json).
  Тип значения определяется Key-объектом/реальным типом — новые ключи попадают
  в экспорт автоматически, без правок кода.
- **НЕ переносится** (честно помечено в UI): медиа-кэш и офлайн-загрузки —
  отдельные файлы (перескачивание); кэш алертов и штамп миграции —
  пересоздаются сами; WorkManager-джобы — перепланируются.
- Формат: JSON `format=1` с секциями `keys` (DataStore) / `sp` (equalizer) /
  `session` (сессия), имя `pinok_settings_ГГГГММДД_ЧЧММСС.json`, место
  сохранения выбирает юзер (SAF). Импорт: чужая версия формата отклоняется
  целиком, битые ключи пропускаются по одному, применение после подтверждения
  с числом записей. Атомарность по хранилищам: DataStore — одна транзакция
  (либо все ключи, либо ни один), equalizer/сессия — пакетно.
- **Безопасность**: файл содержит данные входа в аккаунт — предупреждение в
  UI до экспорта; хранить только у себя, не передавать никому.

### 5.1. Волна 45-в #RESTORE-SAFETY — перепроверка механизма восстановления

По запросу «не хочу ничего терять» восстановление перепроверено и усилено
(свит хранилищ 47-a: покрытие экспорта полное — 169 ключей DataStore/5 типов,
equalizer, сессия; других хранилищ настроек в контейнере нет):

- **Страховочная копия**: перед ЛЮБЫМ импортом текущее состояние целиком
  экспортируется в приватный файл приложения (`filesDir/sova_prefs_safety.json`);
  неудача копии = импорт отменяется ДО единой записи. Копия видна во вкладке
  «Данные» карточкой «Страховочная копия перед импортом» (дата, записи,
  версия) и восстанавливается одной кнопкой — SAF не нужен. Восстановление
  ИЗ копии саму копию не перезаписывает.
- **Guard конфликта типов**: `Preferences.Key` в DataStore равен только по
  имени — запись значения чужого типа под имя живого ключа порождала бы
  ClassCastException при каждом чтении настройки (краш-луп без возврата во
  вкладку импорта). Теперь конфликтный ключ пропускается с честным счётчиком.
- **Честный результат** (тост по секциям): настроек N (пропущено M — конфликт
  типов), эквалайзер K, сессия S из T; непишущиеся SP-файлы (commit()==false)
  и несостоявшаяся сессия видны явно; рекомендация перезапустить приложение.
- **Парсинг**: дубли имени в файле — last-wins со счётчиком skipped; счётчик
  показывается в диалоге подтверждения. Кодировка значений покрывает полный
  набор типов DataStore (float/double/bytes-base64 — forward-compat).
- **Устойчивость UI**: весь IO на Dispatchers.IO, ошибки ловятся
  (try/catch/finally) — зависший busy и краш процесса при неудачном
  импорте/экспорте исключены.
- **Сессия**: commit() проверяется, account.json — best-effort,
  Set<String> не теряется молча.

### 5.2. Волна 45-д #SETTINGS-CRYPTO — шифрование файла экспорта

Запрос пользователя: тумблер включает/выключает шифрование экспорта, а при
импорте зашифрованного файла окно ввода кода открывается независимо от
тумблера. Реализовано ровно так:

- **Тумблер «Шифровать файл настроек»** (Настройки → Данные, карточка
  экспорта): включён → код запрашивается в диалоге ПЕРЕД SAF-пикером
  (ввод + повтор, минимум 4 символа), файл пишется зашифрованным; выключен →
  обычный plaintext-экспорт (как в 45/45-б/45-в).
- **Импорт всегда умеет оба формата**: заголовок конверта (`format=2` +
  `cipher`) распознаётся автоматически — открывается окно «Файл зашифрован»
  с вводом кода, даже если тумблер выключен (файл мог прийти с другой
  установки). Неверный код = GCM-тег не сходится → честная ошибка в поле,
  диалог остаётся открытым (retry без повторного выбора файла).
- **Код нигде не хранится**: ни в контейнере, ни в файле — только тумблер
  (`settings_export_encrypt` в DataStore). Вводится при каждом экспорте и
  при импорте. Потеря кода = потеря файла (написано в диалоге).
- **Криптография** (SovaPrefsCrypto, без новых зависимостей — javax.crypto):
  AES-256-GCM (аутентифицированное шифрование, IV 12Б, тег 128Б) + ключ из
  кода через PBKDF2 (соль 16Б случайная на экспорт): API 26+ →
  PBKDF2WithHmacSHA256/200k итераций, API 24/25 → PBKDF2WithHmacSHA1/300k.
  Алгоритм KDF читается из ФАЙЛА (поле `kdf`), не по версии устройства —
  файл с нового телефона расшифровывается на старом.
- **Формат конверта** (`format=2`, payload `format=1` внутри base64-поля
  `data`): `{"format":2,"cipher":"AES-GCM","kdf":..,"iter":..,"salt":..,
  "iv":..,"data":..}`. Старые v1-файлы читаются как раньше; парсер payload
  честно отказывает на ещё не расшифрованном конверте.
- **Границы**: страховочная копия НЕ шифруется сознательно (не покидает
  приватный контейнер, должна восстанавливаться без трения); PBKDF2 на IO
  (~1 сек); код живёт в памяти как String — от дебаггера/дампа защиты нет
  (тот же класс, что access_token в account.json); рут читает контейнер
  целиком — шифрование защищает файл ЗА пределами устройства (Downloads,
  облако, чужой ПК), а не сам контейнер.

### 5.3. Волна 50 #SESSION-PASSWORD-MATRIX — пароль аккаунта только в шифроконверте

Внешнее ревью (P0): access_token при утечке отзывается, `last_password` — нет;
plaintext-экспорт с паролем внутри = перманентная компрометация аккаунта при
утечке файла (умножение прецедента account.json). Матрица:

| Экспорт | Токены сессии | last_password |
|---|---|---|
| Тумблер ВКЛ (конверт format=2) | внутри шифроконверта | внутри шифроконверта |
| Тумблер ВЫКЛ (plaintext) | включены (отзываемые) | **НЕ включается** |
| Чекбокс «Экспортировать без сессии» | не включаются | не включается |

- `SovaPrefsBackup.export(includeSession, includeSessionPassword)`:
  plaintext-файл строится без `last_password`
  (`ExchangeTokenStorage.KEY_LAST_PASSWORD` — companion открыт ради одной
  константы, без дубля литерала); файл штампуется
  `"sessionPasswordIncluded":false` (у файлов 45–45-д поле отсутствует →
  парсер читает `true` — обратная совместимость).
- Чекбокс «Экспортировать без сессии» — локальное состояние вкладки
  (не настройка): безопасный дефолт — сессия включена. Красное
  предупреждение «файл содержит данные входа» показывается только когда
  сессия действительно попадёт в файл.
- Импорт: по штампу диалог подтверждения предупреждает «пароля аккаунта
  в файле нет — сессия восстановится, но после её слёта потребуется
  повторный вход».
- Страховочная копия (filesDir) ВСЕГДА полная, с паролем: не покидает
  приватный контейнер (UID-изоляция, прецедент account.json) и должна
  восстанавливаться без трения — точка возврата на живой установке.
- Тост экспорта честен: «(файл зашифрован кодом)» / «(без сессии)» /
  «(без пароля аккаунта)».
