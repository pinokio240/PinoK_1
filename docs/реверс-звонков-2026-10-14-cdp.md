# Реверс-инжиниринг веб-звонков VK по захвату CDP (2026-10-14)

Источник: самостоятельный захват трафика через CDP (`tools/.../traffic-capture`),
вкладка https://vk.ru/calls в дебаг-Chrome. В захвате `capture-20261014-194816/capture.har`
полностью отработали: **2 входящих звонка** (один принят, второй отклонён) и **1 исходящий**.

## 1. ГЛАВНОЕ ОТКРЫТИЕ — транспорт сигналинга

Современный веб-VK (SDK **2.8.13-beta.6**, `platform: vk_web2`) сигналит звонки НЕ по
WebSocket к `videowebrtc.okcdn.ru`, а через **WebTransport / HTTP/3 (QUIC)** —
везде `signaling_transport:"wt"`. Прямых WS-кадров звонков в захвате НЕТ (единственный WS —
это eh.vk.ru событийный канал subscribe_to_channels).

Это расходится с нашим прежним реверсом (транспорт WS к videowebrtc.okcdn.ru) — тот устарел
или является альтернативным путём.

## 2. Команды начала звонка — по HTTP (calls.okcdn.ru/fb.do)

### Исходящий звонок — `vchat.startConversation`
```
POST https://calls.okcdn.ru/fb.do
  conversationId = 9431d185-fa24-4bb6-b743-d17a293a8858   # = vcid (UUID)
  isVideo = false
  protocolVersion = 5
  payload = {"is_video":false,"with_join_link":false,"join_by_link":false,
             "community_user_id":0,"caller_app_id":6287487}
  onlyAdminCanShareMovie = false
  externalIds = 152094335                                 # user_id получателя
  method = vchat.startConversation
  format = JSON
  application_key = CGMMEJLGDIHBABABA
  session_key = -w-fl0000MtRwXi530014We...                # из system.getInfo
```
Применение: полностью совпадает с нашей реализацией (`vchatStartConversation` в VKApiClient,
caller_app_id=6287487, externalIds=user_id). Подтверждено живым звонком.

### Вспомогательные fb.do-методы
- `system.getInfo` — получение session_key (STUN/TURN-конфиг), вызывается перед каждым звонком.
- `auth.anonymLogin` (был в захвате 1) — получение session_key/токена SDK.
- `vchat.clientStats` — аналитика (call_init/call_start/...).

## 3. Хронология входящего ПРИНЯТОГО звонка (vcid 762c1915…)
События из `vchat.clientStats` по времени:
1. `call_init` (source=incoming, topology=D)
2. (API) `messages.getCurrentCalls` + `system.getInfo` + `messages.getCallParticipants`
3. `webtransport_connected` (local relay 91.231.135.149 ↔ remote srflx 95.26.29.245, udp)
4. `signaling_connected`
5. `sdp_received: offer` (+ srflx/relay ICE)
6. `call_start`
7. `call_accepted_incoming` (+15с — принятие через 15с)
8. `sdp_generated: answer`; `first_media_received`/`first_media_sent`
9. `call_finish (reason=hangup)`

Сигналинг-команды входящего (summary): `accept-call`, `get-rooms`, `change-media-settings`,
`update-media-modifiers`, `transmit-data`, `custom-data`, `feedback`.

## 4. Хронология входящего ОТКЛОНЁННОГО звонка (vcid 91c60d76…)
1. `call_init` (incoming) → `system.getInfo` → `webtransport_connected` → `sdp_received: offer`
2. `call_start`
3. `call_finish (reason=rejected)` через ~6с — отклонён/не принят.

## 5. Хронология исходящего звонка (vcid 9431d185…, user 152094335)
1. `call_init` (source=outgoing)
2. `api_call: system.getInfo` → `api_call: vchat.startConversation`
3. `webtransport_connected` → `call_start` → `sdp_generated: offer`
4. `sdp_received: answer` (+ srflx/relay) → `call_accepted_outgoing`
5. `first_media_received`/`first_media_sent` → `call_finish (reason=hangup)` (~13с)

Сигналинг-команды исходящего: `update-media-modifiers`, `change-options`,
`change-media-settings`, `transmit-data`, `custom-data`.

## 6. Ключевые сигналинг-команды (сведено из обоих звонков)
accept-call, get-rooms, change-media-settings, update-media-modifiers, transmit-data,
custom-data, feedback, change-options + ping (signaling_ping_summary через WT).

## 7. Выводы для PinoK
- Начало звонка (`vchat.startConversation`) в нашей реализации **корректно** (HTTP fb.do,
  caller_app_id=6287487, payload с is_video/with_join_link). Совпадает с живым веб-трафиком.
- При входящем: web дёргает `messages.getCurrentCalls` и `messages.getCallParticipants` —
  полностью совпадает с нашим кодом (queuev4 '-1' → messagesGetCurrentCalls).
- Различие по транспорту сигналинга: web использует WebTransport ("wt"), мы — WS/HTTP.
  Это объясняет, почему в захвате нет WS-кадров видеовебртк. Для PinoK это означает, что
  таргет сигналинга в вебе обновился; если наш WS-сигналинг не работает — кандидат — переход
  на WebTransport (или подтверждение, что сервер ещё принимает старый WS-протокол).
- Итог: протокол ЗВОНКА (команды) у нас верный; вопрос только в транспортном канале сигналинга.
