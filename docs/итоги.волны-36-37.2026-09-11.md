## 1. #LOCKER-UX-2 — тумблеры «Биометрия»/«Блокировка при возврате из фона» без PIN

- **Жалоба**: тумблер включён, при возврате из фона PIN-пада нет.
- **Root-cause**: pref писался, но resume-чек MainActivity требует
  `lockerPinHash.isNotBlank()` → включение без установленного PIN было
  молчаливым no-op.
- **Фикс**: включение любого зависимого тумблера без PIN открывает
  PinSetupDialog (PIN задаётся первым); честные подписи для уже сломанного
  состояния («Включено, но PIN-код не задан…»).

## 2. #LOCKER-BG-RECREATE — блокировка не срабатывает после убийства Activity

- **Root-cause** (по логу юзера): все возвраты из фона шли через `onCreate`
  при живом pid (Don't keep activities); resume-чек молчал, т.к. флаг
  `isBackgrounded` был полем экземпляра и умирал вместе с Activity.
- **Фикс**: флаг перенесён в companion object (`static @Volatile wasStopped`),
  `onStop` армит только при `!isChangingConfigurations`; recreate-возвраты
  покрыты resume-локером.

## 3. #LOCKER-UX-3 — каскад выключения PIN (запрос пользователя)

- «При отключении пин кода, „Блокировка при возврате из фона" тоже должна
  отключиться. „Биометрия (требует PIN)" — удалить».
- **Сделано**: обе ветки выключения PIN теперь гасят `onBackground` и
  `biometric`; айтем «Биометрия (требует PIN)» удалён из Защиты
  (enum `PinSetupReason` без BIOMETRIC); одноразовая миграция
  `migrateLockerDependentsOff` (SovaApp.onCreate) чистит сломанные состояния
  (биометрия off всегда — писатель удалён; onBackground off при пустом PIN).
- **Откат фичи**: revert айтема + миграции.

## 4. #IM-EMPTY-HONEST — «Нет сообщений» при существующих сообщениях

- **Root-cause**: `messagesGetHistoryWithProfiles` имел 5 молчаливых путей в
  пустой результат (офлайн-гейт; call()=null; ответ без response/items;
  all-or-nothing парсинг — одно кривое сообщение убивало весь чат), и все
  показывались как «Нет сообщений».
- **Фикс**: `HistoryResult.failure: String?` — честная причина в UI
  («Ошибка: …») + кнопка «Повторить» (перезапуск загрузки без выхода из чата);
  парсинг изолирован по айтемам; AppLog-крошки в NETWORK-категории.

## 5. #LOCKSCREEN-FIX — lock-screen плеер видео «как у аудио»

- **Root-cause** (по исходнику media3 1.8.0): MediaSessionService узнаёт о
  сессии только через `addSession()`/`onGetSession()` (последний — только на
  BIND контроллера или ACTION_MEDIA_BUTTON). Видео стартовалось
  startForegroundService с «голым» интентом → сессия не регистрировалась →
  media3 никогда не строил MediaStyle-нотификацию; на lock-screen была только
  невидимая MIN-заглушка #VIDEO-FG-TIME. Аудио работало через bind-путь
  (PlayerConnection → MediaController → onGetSession → addSession).
- **Фикс** (VideoPlaybackService.onCreate): явный `addSession(builtSession)`
  (идемпотентно) + явный DefaultMediaNotificationProvider с ID 41102 (= ID
  заглушки → замена 1:1, без коллизии с аудио-нотификацией =1001);
  `@OptIn(UnstableApi::class)`.
- **Проверка**: видео играет → свернуть/заблокировать → на lock-screen
  медиа-плеер (play/pause, ±N сек, название); пауза/плей с локскрина;
  возврат в приложение убирает уведомление.

## 6. #AUDIO-COMMENTS — аудио треки в комментариях не воспроизводились

- **Жалоба**: «Аудио треки в комментариях не воспроизводятся».
- **Root-cause, 2 слоя**:
  1. `CommentAttachmentsView` (общий рендер вложений комментариев:
     PostDetailScreen + CommentsBottomSheet ленты) рендерил аудио статичной
     `CommentAudioRow` **без click-обработчика** («без плеера — как VK web») —
     тап ничего не делал. Аудио постов при этом везде кликабельно.
  2. Риск: VK в аудио-вложениях (особенно `wall.getComments`) часто не отдаёт
     `url`; `playTrackList` фильтрует треки без URL (Fix #59) → тап давал
     «Нет воспроизводимых треков» или стартовал соседний трек.
- **Фикс**:
  - `CommentAttachmentsView`: аудио комментария собираются в список и
    рендерятся блоком `AudioAttachmentList` (тап = play/pause, треки
    комментария = очередь, подсветка текущего, мини-плеер); `CommentAudioRow`
    удалена.
  - `AudioAttachmentList`: тапнутый трек без URL резолвится перед запуском
    через `audioGetById` (audio.getById quality=hq + #AUDIO-UNMASK +
    al_audio.php web-fallback §42.12 — путь загрузок #DL-DISPATCH-RESTORE);
    неудача → честный Toast «Не удалось получить ссылку на трек — нет доступа
    к аудио» (GlobalMiniPlayer playerState.error не рендерит).
- **Проверка**: открыть пост с аудио в комментариях → тап по треку → играет,
  мини-плеер появился; повторный тап = пауза. Если Toast — прислать logcat
  (категория NETWORK): строки `audioGetById: API returned no url …` /
  `al_audio.php fallback` покажут, где VK отказал.
