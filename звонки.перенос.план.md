## §3. Архитектурные решения

1. **Фасад.** `CallsApi` расширяется волнами (A/Б/В по §2) — добавление членов не нарушает канон
   §3.2 (состав 8 членов `CallsDependencies` фиксирован). Все новые методы — в `VKApiClient`
   с KDoc-маркером `#CALLS-SNAP` (трассировка на этот план).
2. **Репозиторий раздела.** Новый `CallsSectionRepository` (в `:app`, публикуется через
   `CallsContainer` capability): `StateFlow`-состояния списков (история, пропущенные, записи,
   расшифровки, запланированные, активные) + кэш + инвалидация по событиям (завершение звонка,
   LP-события). Секции читают репозиторий вместо собственного `remember{}` — единый источник
   правды, бейдж пропущенных, меньше повторных запросов. I/O — только на `Dispatchers.Default`
   (#ANR-MAIN-IO: 2516 записей истории — тот же класс патологии, что и офлайн-плеер).
3. **Навигация.** `CallsMainScreen` — сайдбар из 8 пунктов (`CallsTab` enum расширяется), роуты:
   `calls_history` (существующий хост) + внутренние табы; новые: `calls_recordings`,
   `calls_transcripts`, `calls_scheduled`, `calls_active`, `call_chat/{callId}`,
   `incoming_call`. Мёртвые секции (`CallsActiveSection`, `CallsRecordingsSection`,
   `CallsTranscriptsSection`, `CallsScheduledSection`, `CallsHomeSection`) — оживить и доработать
   (не выбрасывать: код переиспользуется).
4. **Входящий.** `IncomingCallScreen` (полноэкранный, route `incoming_call`, параметры payload)
   + `IncomingCallBanner` (свёрнутый виджет, overlay в корне NavHost) — обе фазы поверх навигации,
   запуск из существующего механизма `pendingIncomingCallPayload`.
5. **In-call расширения.** CallScreen сохраняет свою машину состояний (риск-зона: reanswer/zombie
   и пр. не трогаем); новые панели (участники/чат/настройки/реакции) — отдельные Composable с
   собственным состоянием, коммуникация через сигналинг-клиент.
6. **Видео-флаг.** `CallStarter.startCall(peerId, video)` уже принимает video — прокинуть флаг
   во всю цепочку (диалоги redial, шапка чата) — сами камеры остаются Этапом 2.2 (старый план),
   но кнопка «Видеозвонок» обязана реально слать `video=true` (сервер и так поддерживает приём
   видео: `callsVideoRx` уже реализован).
7. **BuildStamp** bump в каждом коммите этапов (звонковая цепочка меняется всегда).
8. **No-stub policy.** Критерий готовности этапа: каждый контрол матрицы §1, входящий в этап,
   имеет реальный обработчик с реальным API-вызовом; «Позже»-диалоги запрещены. Чек-лист
   приёмки — §4-И.

## §4. Этапы внедрения

### Этап А — Фасад, репозиторий, каркас раздела (база для всего)
- A1. `VKApiClient` + фасад `CallsApi`: волна 1 — §2.1 (история: marker/filter, group-history,
  delete/clear, missed) и §2.2 (ASR). Волна 2 — §2.3/§2.4 (планирование, join-link, участники,
  настройки, conversation-by-call). KDoc `#CALLS-SNAP`.
- A2. `CallsSectionRepository` (StateFlow + кэш + инвалидация), capability в `CallsContainer`.
- A3. Сайдбар 8 пунктов + «Настройка пунктов меню» (порядок/видимость, persist SovaPrefs).
- A4. Общий вид строки-кластера истории (статусы/даты/длительности, аватар группы), общий
  паттерн loading/error/empty с рабочим «Повторить» (текущий баг: repeat не перезагружает).
- ✅ Готовность: фасад компилируется, репозиторий отдаёт данные, сайдбар переключает 8 пустых
  живых табов, повтор реально тянет данные.

### Этап Б — История и Пропущенные (матрица §1.2, §1.3)
- Б1. История: `calls.getHistory` c пагинацией (scroll→pagination_marker), кластеризация,
  статусы «Завершённый/Пропущенный/Отменённый/Групповой · длительность · вчера/сегодня/дата».
- Б2. Redial «Аудиозвонок X» / «Видеозвонок X» (video-флаг сквозь CallStarter).
- Б3. «Действия»: удалить записи (`deleteHistoryRecords`), очистить историю (`clearHistory`),

- Б4. Пропущенные: фильтр missed, кластеры со счётчиками, бейдж в сайдбаре (репозиторий),
  те же действия.

## §5. Риски и ограничения

1. **Групповые/SFU**: топология SERVER частично реализована; Ж9 (залы) и Ж8 (зал ожидания)
   требуют устойчивой SERVER-сессии — перед Ж9 обязательный стабилизационный прогон групповых.
2. **Wire-неизвестные**: команды Ж2/Ж6/Ж7/Ж8/Ж9 не покрыты реверсом PinoK — этап Ж-0 обязателен,
   формат может потребовать итераций (как LP 115 в своё время).
3. **Медиапроекции/фон/vmoji (Ж11)**: нативные аналоги тяжёлые; каждый — отдельный подэтап
   с собственным чек-листом; порядок внутри Ж11 — по согласования с юзером.
4. **Объём**: Этапы А–Е — компактные и быстрые (в основном UI+фасад поверх уже работающих
   API-цепочек); Ж — основная трудоёмкость.
5. **Бэкенд-флаги VK**: некоторые тумблеры `calls.getSettings` могут зависеть от аккаунта —
   переключатель без серверного флага честно отобразит состояние сервера (не заглушка:
   читаем реальное значение, пишем реальный `setUserSettings`).

## §6. Порядок относительно канона контейнеризации

Очередь §3.7 (`контейнеры.план.md`) не нарушается: п.2 (аудио) может идти параллельно этапам
А–В настоящего плана (модули не пересекаются: `:feature:audio` vs `:feature:calls`+`:app`).
Этапы Г–Ж трогают `CallScreen`/сигналинг — с ними п.2 аудио сериализуем (общие файлы
`:app`-хоста). Звонковая волна «Д» канона (перенос оставшихся зависимостей в контейнер)
поглощается этапом А настоящего плана (репозиторий публикуется как capability — по канону).
